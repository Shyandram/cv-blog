## The big picture

A conversation is a changing shared problem. The latest sentence may replace a previous request, refer to an earlier object, or correct the system's interpretation. Understanding each sentence alone is insufficient. The system must track who said what, what remains uncertain and which proposal the participants have actually accepted.

## 1. Discourse connects meanings beyond a sentence

Discourse is language organized across clauses or sentences. Coherence is the relationship that makes those pieces understandable together. Relations can be explicit, as in a sentence introduced by “because,” or inferred from context. A system must distinguish a relation stated by the source from one merely suggested by proximity.

Consider “The pump warmed. The operator stopped it.” The two sentences introduce an event, an agent and a reference to an object. They may suggest a response to warming, but they do not necessarily prove that warming caused the stop. Adding “because” changes the expressed relation. A summarizer that inserts it has added a claim, not simply improved style.

Represent a discourse as a graph $G=(V,E)$, where $V$ contains text segments or propositions and $E$ contains typed relations. A relation can indicate explanation, contrast, temporal order, elaboration or reference. The representation is a modeling choice; not every discourse dependency fits a single tree. Entity reference may connect distant segments that belong to different local topic units.

The useful first question is operational: which relationships must the application preserve? For an incident query, keep event times, entity identities, negation and evidence links. For a conversational tutor, also keep the learner's question and any unresolved misunderstanding. A general discourse label becomes useful when its errors can be connected to an actual application outcome.

Syntax and discourse contribute different evidence. A grammatical subject can be prominent, a recently discussed entity can remain salient, and an explicit topic shift can change the preferred referent. These are cues, rather than universally valid rules. A model trained to prefer recent mentions may fail when the conversation deliberately returns to an earlier object.

McRoy [2] provides the conceptual reading for coherence, reference and the interactive management of meaning. In an implementation, retain source offsets and the original utterance alongside any graph or extracted propositions. A mistaken interpretation should be traceable to evidence, and a later correction should be able to replace the interpretation without deleting the original record.

## 2. Mentions, antecedents and coreference

A mention is a text span that refers to an entity, event or concept. An antecedent is an earlier expression that helps interpret another mention. Coreference groups mentions that refer to the same entity. Similar wording does not necessarily imply identity: two different pumps may both be called “the backup pump.”

A span-based coreference model can score possible antecedents for a mention, as illustrated by Lee et al. [3]. Abstractly,

$$
p(a_i=j\mid d)=\frac{\exp s(i,j,d)}{\sum_{k\in A_i}\exp s(i,k,d)}.
$$

Here $d$ is the document or conversation; $i$ indexes the current mention; $A_i$ is the set of candidate antecedents, including a null option; $a_i$ is the selected antecedent variable; and $s(i,j,d)$ is a learned compatibility score. The null option permits a mention to introduce a new entity or remain unlinked. Candidate pruning changes what the model can consider.

The model must detect mentions as well as link them. If an earlier entity span was discarded, a later linking decision cannot recover it merely by assigning better scores among remaining candidates. Separate detection recall from linking accuracy when diagnosing failures. For a task system, linking to the wrong device can matter more than omitting an irrelevant mention.

The following hand-written baseline uses explicit compatibility and recency. It is deliberately small enough to expose a failure. Device categories are supplied as data; the code does not infer attributes from personal names or social stereotypes.

```python
entities = [
    {"id": "pump_a", "category": "device", "turn": 1},
    {"id": "valve_b", "category": "device", "turn": 2},
    {"id": "operator", "category": "person", "turn": 2},
]
def candidates(category):
    return [e for e in entities if e["category"] == category]
def recent(category):
    choices = candidates(category)
    return max(choices, key=lambda e: e["turn"])["id"] if choices else None
print("Recency baseline for it:", recent("device"))
assert recent("device") == "valve_b"
# In a synthetic annotation, the speaker meant the earlier pump.
intended = "pump_a"
assert recent("device") != intended
# A cautious application preserves ambiguity instead of hiding the choice.
possible = {e["id"] for e in candidates("device")}
resolution = next(iter(possible)) if len(possible) == 1 else None
assert resolution is None and possible == {"pump_a", "valve_b"}
```

The baseline chooses the most recent compatible entity, while the constructed speaker intention points to the earlier pump. The point is not that recency is useless; it is that a cue cannot establish identity in every case. A clarifying question such as “Do you mean Pump A or Valve B?” preserves the uncertainty explicitly.

Context can include deixis: expressions such as “this,” “here” or “now” depend on a speaker, place, time or interface selection. Store the relevant context with the utterance. A written transcript without the original interface selection may not contain enough evidence to resolve “this device.” Do not score a system as wrong for refusing an inference that the provided input cannot support.

Evaluation also depends on the annotation policy. Some corpora link only entities; others include event references or associative relations. Decide whether a null link is allowed and how ambiguity is annotated. A score is interpretable only relative to that definition. This chapter uses explicit synthetic entity IDs so the intended scope is visible.

## 3. Turns, acts and shared state

A dialogue turn is a participant's contribution at a particular point in an exchange. Its function can be a request, an answer, a correction, a confirmation or a clarification. The same surface word can have different functions depending on the pending question: “Tuesday” may supply a date or correct an earlier date.

A task-oriented dialogue state stores the information needed to continue a specified task. For the equipment query, slots might include device, time interval, measurement and output language. Store values together with source turn, confidence and status. Unknown, explicitly absent and not applicable should not collapse into one empty string.

Write a state update as

$$
s_t=U(s_{t-1},o_t,r_t),\qquad a_t=\pi(s_t).
$$

Here $s_t$ is the state after turn $t$; $o_t$ is the observed utterance or extracted dialogue act; $r_t$ identifies the speaker and other turn context; $U$ is the update rule; $a_t$ is the next system action; and $\pi$ is the policy mapping state to actions. The state need not be a single deterministic record, and the policy need not generate text directly.

Keep proposal state separate from committed state. A user may ask for an option, inspect it and then change it. The system's own suggestion does not become a user preference merely because it appears in the transcript. Similarly, a quoted document saying “replace Pump A” is evidence content, not an instruction from the current user.

Corrections require scope. “Actually, Pump B” can replace the selected device while keeping the time interval. “Start over” may discard the whole task. “Not yesterday” rejects a value without necessarily specifying a replacement. A state tracker should represent these distinctions before a generator writes a response.

Multi-party dialogue adds ownership. One participant's preference need not override another participant's instruction. A shared task should specify which participant can confirm a change and which facts are observations rather than preferences. Speaker labels, timestamps and conversation IDs belong to the data model, not merely to decorative transcript formatting.

## 4. Belief states and useful clarification

When an utterance is ambiguous, a belief state can retain several interpretations. The system can then choose whether to act, retrieve more evidence or ask a question. A maximum-probability interpretation is not automatically safe to execute; the consequence of a mistake matters.

A simple Bayesian update is

$$
b_t(h)=\frac{p(o_t\mid h)b_{t-1}(h)}{\sum_{h'}p(o_t\mid h')b_{t-1}(h')}.
$$

Here $h$ is a candidate interpretation; $b_{t-1}(h)$ is its previous probability; $o_t$ is the new observation; $p(o_t\mid h)$ is its likelihood under the interpretation; and the denominator normalizes over candidates $h'$. This simplified update assumes a fixed hypothesis space and a specified observation model. A changing task needs a transition model or an explicit correction operation rather than repeatedly treating every utterance as independent evidence.

```python
import numpy as np

hypotheses = ["pump_a", "pump_b", "unknown"]
prior = np.array([0.48, 0.48, 0.04])
ambiguous_likelihood = np.array([0.6, 0.5, 0.2])
posterior = prior*ambiguous_likelihood
posterior /= posterior.sum()
print("After ambiguous evidence:", dict(zip(hypotheses, posterior.round(3))))
action = "clarify" if posterior.max() < 0.9 else "query"
assert action == "clarify"
# A second synthetic observation explicitly names Pump B.
named_likelihood = np.array([0.02, 0.95, 0.03])
updated = posterior*named_likelihood
updated /= updated.sum()
print("After explicit naming:", dict(zip(hypotheses, updated.round(3))))
assert updated[1] > 0.9
assert np.isclose(updated.sum(), 1)
```

The likelihoods are constructed for the teaching example. They are not calibrated model scores or measured human behavior. In a learned system, calibration and uncertainty under distribution shift require validation. Retaining an unknown hypothesis also prevents a closed list from pretending that every real request refers to a known device.

<Figure src={belief} alt="Synthetic belief probabilities over Pump A, Pump B and unknown before evidence, after an ambiguous observation and after explicit naming." caption="Figure 1 — A belief state preserves ambiguity until additional evidence changes the decision. The probabilities are constructed for the example and do not claim empirical calibration." />

A decision-theoretic policy minimizes expected loss: $a^*=\operatorname*{arg\,min}_a\sum_h b_t(h)L(a,h)$. Here $a$ ranges over permitted actions and $L(a,h)$ is the cost of action $a$ when interpretation $h$ is true. Asking a question has a cost, but querying the wrong device may have a larger one. A fixed confidence threshold is an illustrative shortcut to this policy, not a universal optimal rule.

Ask the question that distinguishes the uncertainty that matters. If only the device is ambiguous, do not request the already established time interval again. If the request is unsupported by the application's schema, explain that limitation instead of asking for an irrelevant detail. A clarifying question should change the feasible next actions, not merely prolong the exchange.

Information gain and task utility differ. A question can reduce uncertainty about an irrelevant preference while leaving the device unresolved. Measure whether the answer enables a correct continuation. Repeated clarification can also frustrate users, so evaluate recovery success and interaction cost together.

## 5. A deterministic state tracker with correction tests

A structured state tracker is a useful baseline for a narrow task. It reveals the contract between language understanding and action selection. The next example consumes already extracted events; it does not claim to understand arbitrary natural language.

The state stores selected slots and a revision counter. Any accepted slot change invalidates the previous confirmation. A confirmation is valid only for the revision explicitly presented to the user. This prevents an old “yes” from authorizing a newly changed proposal.

```python
from copy import deepcopy

initial = {"device": None, "period": None, "revision": 0, "confirmed": None}
def update(state, event):
    result = deepcopy(state)
    kind = event["kind"]
    if kind == "set":
        slot, value = event["slot"], event["value"]
        allowed = {"device": {"pump_a", "pump_b"}, "period": {"today", "yesterday"}}
        if slot not in allowed or value not in allowed[slot]:
            raise ValueError("Unsupported slot or value")
        if result[slot] != value:
            result[slot] = value
            result["revision"] += 1
            result["confirmed"] = None
    elif kind == "confirm":
        if event["revision"] != result["revision"]:
            raise ValueError("Confirmation refers to an old proposal")
        if any(result[k] is None for k in ["device", "period"]):
            raise ValueError("Cannot confirm incomplete state")
        result["confirmed"] = result["revision"]
    else:
        raise ValueError("Unsupported event")
    return result
s1 = update(initial, {"kind": "set", "slot": "device", "value": "pump_a"})
s2 = update(s1, {"kind": "set", "slot": "period", "value": "today"})
s3 = update(s2, {"kind": "confirm", "revision": 2})
s4 = update(s3, {"kind": "set", "slot": "device", "value": "pump_b"})
print("Before correction:", s3)
print("After correction:", s4)
assert initial["device"] is None
assert s3["confirmed"] == 2 and s4["confirmed"] is None
try:
    update(s4, {"kind": "confirm", "revision": 2})
except ValueError:
    pass
else:
    raise AssertionError("Stale confirmation was accepted")
```

<Figure src={state} alt="Synthetic dialogue-state timeline: device and period are selected, revision two is confirmed, then a device correction creates revision three and invalidates confirmation." caption="Figure 2 — Corrections change state and confirmation scope. Keeping a revision makes stale acceptance visible rather than silently applying it to a different proposal." />

The copy preserves previous states for inspection and testing. A real system also needs event IDs so a repeated delivery does not apply the same update twice. Distinguish a repeated observation from a new correction that happens to have the same text. Store the source turn and parsed event so an error can be traced to language understanding or state logic.

Do not equate absence of a slot with a negative assertion. “No fault occurred” fills a fault-status value; an unmentioned fault leaves it unknown. If a user retracts a value, the tracker should clear or revise it explicitly. An append-only transcript without state interpretation will retain both the old and new values; retrieval can later return either unless status is preserved.

The baseline's narrow allowed values make its coverage obvious. General systems can use learned slot extraction and open vocabulary values, but should still validate units, schema and provenance. A model's confidence is not a substitute for a legal value. Test the interface between extraction and state updates with malformed, unsupported and contradictory events.

## 6. Context windows, summaries and persistent memory

A long transcript contains more information than the next response needs. Truncating it can remove a still-active constraint, while summarizing it can alter scope or certainty. Memory should retain what remains relevant and distinguish accepted state from historical suggestions.

Partition context into recent turns, structured task state and retrieved evidence. Recent turns support local reference and tone; state stores accepted slots and unresolved questions; evidence supports factual claims. These sources have different roles. A summary should not promote an unverified model response into authoritative evidence.

A useful memory record includes a value, its source, time, scope and status. Scope can be one request, one conversation or a persistent preference. A correction should update the active record and leave a trace of the earlier one. Persistent storage needs a deliberate policy; do not assume every detail a user mentions should affect future conversations indefinitely.

Represent a record as $m=(v,p,\tau,\sigma,q)$, where $v$ is the value, $p$ is provenance, $\tau$ is time, $\sigma$ is scope and $q$ is status such as proposed, accepted or retracted. This tuple is an application schema rather than a standard linguistic formalism. Its purpose is to make interpretation and retrieval auditable.

A rolling window may contain “yes” while excluding the proposal it answered. A summary may retain a device but omit that it was replaced by another. Test both with synthetic conversations. Compare the reconstructed state with an explicit event log, not merely whether the generated reply sounds coherent.

Retrieving older turns can help, but similarity alone is insufficient. A very similar old request can have the wrong timestamp or a retracted value. Filter by conversation, participant and active status before using retrieval scores. Preserve the distinction between an earlier example and the current instruction so the application does not resume a finished task accidentally.

For multilingual dialogue, normalization and translation can change references or politeness. Keep original utterances available to qualified reviewers. An English summary of a Traditional Chinese conversation can be useful, but it needs tests for regional terms, negation and speaker identity. Memory quality is part of the language task, not only a storage optimization.

## 7. Task dialogue and open conversation

Task-oriented dialogue has a defined outcome: supply a query, complete a booking-like record, retrieve the right observation or produce a specified report. Open conversation has less sharply defined goals and more acceptable replies. Both require consistency, but their success criteria differ.

A modular task system separates understanding, state tracking, policy, evidence access and realization. This makes errors easier to locate. A learned end-to-end system can combine these functions, but it still needs tests that distinguish wrong state from poor wording. Hagiwara's conversational sequence-model reading [1] is a starting point; the surveys [4,5] describe broader design families.

For response generation, write $p_\theta(u_t\mid h_t,s_t,e_t)$, where $u_t$ is the next utterance, $h_t$ is selected history, $s_t$ is task state, $e_t$ is evidence and $\theta$ is the model parameters. The conditional distribution says what the generator receives. It does not ensure that the generator respects every state field or evidence item.

A task policy can choose clarification, query, explanation or refusal of an unsupported operation. Generation then verbalizes that action. This distinction keeps conversational fluency from deciding whether a query is ready. A deterministic policy may be a strong baseline when the legal actions and state schema are limited.

Open conversation benefits from flexible language, but persona or style should not override factual consistency. A system can be engaging while inventing past interactions or implying it performed an action that never occurred. Evaluate claims about the conversation against the actual log, and claims about external facts against evidence. Those are separate checks.

The application also needs a clear completion condition. A task may end when the requested report is delivered, while a conversation can continue with a new task. Record that transition so earlier confirmations and slot values do not silently apply to the new request. Reusing a device preference may be appropriate; reusing an authorization for an unrelated operation is not.

## 8. Tool boundaries and grounded action reports

A tool-connected dialogue system generates proposals that software may execute. The proposal, execution and result are distinct events. A sentence saying “I queried the database” should be supported by a successful query result, not merely by the model having generated a query description.

Tool-learning research studies how foundation models plan, select tools, construct arguments and use feedback [6]. An application should expose only its permitted operations through an explicit schema. Validate the selected tool and arguments before execution, then attach the result status and evidence identifier to the state. This is ordinary interface correctness applied to a language-driven controller.

Read-only evidence can contain imperative text. An equipment manual might quote a command, and a retrieved conversation might contain another participant's request. These strings remain source content. They should not update the current user's task state or expand the system's permitted operations. Role and provenance labels must survive retrieval and summarization.

For the synthetic query assistant, only an established device and period can form a query proposal. The system can show a pending proposal and ask for missing information. A result should distinguish success, no matching observation and execution error. Converting all three into a generic fluent answer erases the information needed to understand what happened.

Repeated attempts need their own state. Retrying a read-only query may be acceptable; repeating an operation that changes external state can produce a second effect. Record request identifiers and execution status, and let the software boundary enforce its semantics. Do not rely on the language model remembering that an action already ran.

This chapter executes no external tools; its state examples stop at proposal tracking. In a real deployment, test the proposal validator and result interpreter separately from language generation. The [generation and deployment chapter](/en/learn/nlp/nlp-08-generation-deployment/) continues with versioned contracts and workload measurements.

## 9. Evaluate a conversation, not just a reply

A correct-looking response can hide a wrong slot, stale memory or unexecuted action. Evaluation should measure intermediate state and final task outcome over complete conversations. Deriu et al.'s survey [4] explains why task-oriented, conversational and question-answering systems require different evaluation methods.

For a specified set of slots $J$, define exact state accuracy as

$$
A_{\mathrm{state}}=\frac{1}{N}\sum_{t=1}^{N}\mathbf1\{\hat s_{t,j}=s_{t,j}\text{ for every }j\in J\}.
$$

Here $N$ is the number of evaluated turns; $s_{t,j}$ is the reference value for slot $j$ at turn $t$; $\hat s_{t,j}$ is the predicted value; and $\mathbf1$ is one when all selected slots match and zero otherwise. This strict measure exposes errors hidden by averaging over mostly empty or easy slots. The selected slot set and handling of unknown values must be specified.

```python
reference = [
    {"device": "pump_a", "period": None},
    {"device": "pump_a", "period": "today"},
    {"device": "pump_b", "period": "today"},
]
predicted = [
    {"device": "pump_a", "period": None},
    {"device": "pump_a", "period": "today"},
    {"device": "pump_a", "period": "today"},
]
slots = ["device", "period"]
joint = sum(all(p[j] == r[j] for j in slots)
            for p, r in zip(predicted, reference))/len(reference)
slot_accuracy = sum(p[j] == r[j] for p, r in zip(predicted, reference)
                    for j in slots)/(len(reference)*len(slots))
print("Exact state accuracy:", joint)
print("Per-slot accuracy:", slot_accuracy)
assert joint == 2/3 and slot_accuracy == 5/6
# The final device is wrong despite many correct fields.
assert predicted[-1]["device"] != reference[-1]["device"]
```

Task success should check the final requested outcome, not just dialogue length or friendly style. For the example, require the correct device, time interval and evidence, with corrections honored. Report unsupported action claims and unresolved references separately. A short conversation that queries the wrong device is not efficient success.

Human evaluation should show enough history to interpret a response and specify the judgment task. A rater who sees only the last reply cannot assess whether a correction was honored. Randomize system identity, define error categories and retain disagreements. Schmidtova et al. [7] show why explicit hallucination definitions and reporting matter for generation evaluation.

Split datasets by conversation and related users or incidents when those groups create leakage. Adjacent turns must not be scattered across train and test. Include challenge conversations with topic changes, repeated names, ambiguous pronouns, corrections, stale confirmations and tool failures. Record whether a user simulator generated examples; simulated success is evidence under that simulator, not automatically evidence of human usability.

Use paired comparisons on the same conversations and report uncertainty at the conversation level. Turns within one conversation are dependent, so a large number of turns does not equal the same number of independent tests. Include repair behavior: whether the system recognizes a misunderstanding, asks a useful question and recovers to the right outcome.

## Modern view

The modern reading map connects linguistic structure, system design and evaluation. Sources were checked through October 4, 2026; survey publication dates and manuscript status are stated rather than treating every source as equally current.

**Ni et al.'s systematic survey [5]**, published in the 2023 volume of Artificial Intelligence Review, organizes deep-learning dialogue by model type and system type. Its task-oriented versus open-domain distinction explains why one response metric cannot characterize every conversation. Our synthesis is to choose an evaluation around the system's actual goal, then inspect the state and evidence failures that goal depends on.

**Deriu et al.'s evaluation survey [4]** separates task-oriented dialogue, conversational systems and interactive question answering. It maps human and automatic evaluation to their different structures. The practical lesson is to measure both components and outcomes: good utterance quality can coexist with a failed task, while strict slot matching can miss an unhelpful clarification strategy.

**Qin et al.'s tool-learning review [6]**, published in 2024, organizes the interaction among foundation models, tools, planning and feedback. It motivates inspecting argument construction and result use alongside text quality. Our application-level conclusion is to maintain proposal, execution and evidence state explicitly. Tool access increases what the system can attempt; it does not remove the need to validate the attempt or report its actual outcome.

**Schmidtova et al.'s 2025 human-evaluation survey [7]** documents variation in how hallucinations are defined and assessed. For dialogue, distinguish inconsistency with conversation history, unsupported external claims and false reports of actions. These categories need different evidence and may require different reviewers. Publishing the annotation instructions makes a score interpretable and reproducible.

| System responsibility | Useful representation | Test that exposes a failure |
|---|---|---|
| Reference | mentions, candidates, entity IDs | two compatible devices and an ambiguous pronoun |
| Task tracking | slots, revisions, source turns | a correction after an earlier confirmation |
| Uncertainty | alternative interpretations or belief state | unclear device followed by explicit naming |
| Memory | provenance, scope and status | an old value retrieved after retraction |
| Tool control | validated proposal and execution status | failed or repeated query with no fabricated success |
| Response | selected action, state and evidence | fluent text that changes a number or reference |
| Evaluation | whole conversations and defined error categories | high per-slot accuracy but a wrong final task |

Current design work increasingly combines flexible generation with explicit state, retrieval and tool interfaces. The surveys support different parts of this map; the table is our teaching synthesis, not a new standardized architecture. A model can improve language flexibility while state logic remains a small deterministic component. Compare that modular baseline before assuming that every responsibility should be learned jointly.

Open problems include reference across long contexts, calibration under task changes, multilingual corrections, stale memories, reliable tool-result interpretation and scalable human evaluation. More context can help recover evidence but also introduces outdated or contradictory material. Test memory selection and status tracking rather than treating a longer context window as a complete solution.

The next research question should be narrow enough to evaluate: “Does explicit revision state prevent stale confirmations?” or “Can a clarifying question recover an ambiguous device reference without asking for already known slots?” Keep a complete conversation trace and a stated success condition. That turns a promising dialogue demonstration into evidence you can inspect.

## Key takeaways

- Discourse requires entity reference, relations and scope beyond isolated sentence meanings.
- Mention detection and antecedent selection are separate sources of coreference error.
- Dialogue state distinguishes proposals, accepted values, corrections and confirmations.
- Belief states preserve ambiguity; clarification should resolve uncertainty that affects the task.
- Memory needs provenance, time, scope and status, with retractions preserved.
- Tool proposals, executions and observed results must remain distinct events.
- Evaluate state, repair and final outcomes over whole conversations with explicit evidence.
