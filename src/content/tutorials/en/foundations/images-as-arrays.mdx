## What you'll learn

- How a grayscale or color image becomes a NumPy array, and what `shape`, `dtype` and `strides` tell you about it.
- Why an image is a *sampled and quantized* version of a continuous scene, and what is lost when you keep fewer pixels or fewer gray levels.
- The coordinate convention (row first, then column), and how slicing, flipping, masking and flattening work, including the difference between a view and a copy.
- The three pitfalls that bite everyone: BGR versus RGB channel order, `uint8` wraparound, and writing through a view by accident.
- How the same array view of an image carries over to deep-learning tensors, image patches and neural image representations.

## The big picture

Every method in this site, from a 3×3 blur to a vision Transformer, starts from the same object: a grid of numbers. If you can read, slice and transform that grid with confidence, the rest of the curriculum is a matter of choosing which numbers to combine and how.

<Callout type="tip" title="Explain like I'm five">
Picture a mosaic made of tiny colored tiles. Stand far away and you see a face; stand close and you see only squares, each with one color. A digital photo is the same: a rectangle of tiles, and every tile is described by a number (or three numbers, one each for red, green and blue). To find a tile you say "which row, which column", the way you find a seat in a cinema. Computers store the mosaic as a table of numbers, and everything you do to a picture, such as brightening it, blurring it or finding faces in it, is arithmetic on that table.
</Callout>

Why it matters: almost every beginner bug in image code is really a bug about the array, not about the algorithm. Colors look blue because the channels were swapped. Bright areas turn black because 8-bit values wrapped around. An edit changes the original because a crop was a view, not a copy. This page names those traps once, with code you can run, so you can recognize them later.

## An image is a sampled, quantized signal

**Plain version.** The real world has no pixels. A camera measures how much light reaches each tiny spot of its sensor, and writes the measurement down as a whole number. Two decisions turn a continuous scene into a digital image: *where* to measure (how many spots) and *how finely* to write each measurement (how many possible values).

**Precise version.** Let a monochrome scene be a continuous brightness function. **Sampling** evaluates it on a regular grid of $H$ rows and $W$ columns. **Quantization** rounds each sample to one of $L = 2^b$ integer levels, where $b$ is the number of bits per pixel. The result is a function on a finite grid,

$$
I : \{0, \dots, H-1\} \times \{0, \dots, W-1\} \to \{0, \dots, L-1\}, \qquad (r, c) \mapsto I[r, c],
$$

where $r$ is the **row** index (counted from the top), $c$ is the **column** index (counted from the left), $I[r, c]$ is the **pixel value**, and $L = 256$ for the common 8-bit case, so values run from 0 (black) to 255 (white). A color image adds a channel index $k$ and becomes $I[r, c, k]$ with $k \in \{0, 1, 2\}$ for the three color channels. This is the standard treatment of image formation and digitization in textbooks such as Gonzalez and Woods [1, Ch. 2] and Torralba, Isola and Freeman [2].

Written as an array, the grid has a **shape** `(H, W)` for grayscale or `(H, W, 3)` for color. The number of values stored is $H \times W \times C$ for $C$ channels, and the memory needed is that count times the bytes per value.

<Callout type="note" title="Coordinates: row first">
Arrays are indexed `[row, column]`, which is `[y, x]` in the picture's own axes: the first index runs down the page, the second runs across. Graphics functions often take points as `(x, y)`, which is `(column, row)`. This series' image-processing chapters follow the textbook convention and write $f(x, y)$ with $x$ as the row index, so $f(x, y)$ matches NumPy's `f[x, y]`. Whenever code and math disagree, check which axis is which before debugging anything else.
</Callout>

## Shape, dtype and memory

**Plain version.** An array knows three things about itself: how many numbers it holds along each axis (`shape`), what kind of number each is (`dtype`), and how those numbers are laid out in memory (`strides`).

scikit-image ships a few small test photographs [6], [7], which keeps every example here runnable without downloading anything. The code below loads one grayscale and one color image and prints their basic properties.

```python
import numpy as np
from skimage import data

gray = data.camera()          # grayscale test photo bundled with scikit-image
rgb = data.astronaut()        # color test photo, also bundled

for name, a in [("gray", gray), ("rgb", rgb)]:
    print(name, a.shape, a.dtype, a.ndim, a.size, a.nbytes)
print(gray.min(), gray.max())
print(gray.strides, rgb.strides)
```

Output:

```text
gray (512, 512) uint8 2 262144 262144
rgb (512, 512, 3) uint8 3 786432 786432
0 255
(512, 1) (1536, 3, 1)
```

Reading the output: the grayscale image has 512 rows and 512 columns, so `size` is 512 × 512 = 262,144 values, and since each `uint8` takes one byte, `nbytes` is the same number. The color image has three times as many values. The pixel range is the full 0 to 255.

`strides` is the number of bytes to jump to move one step along each axis. For `gray`, moving one column costs 1 byte and moving one row costs 512 bytes, which means NumPy stores the image **row by row** (C order). In `rgb`, the three channel values of one pixel sit next to each other in memory. This explains why scanning along a row is fast and why reshaping an image into a long vector keeps rows together, as the next section shows. The NumPy paper [3] and documentation [4] describe the array model in full.

## Indexing, slicing and views

**Plain version.** Because an image is just an array, you pick out pixels, rectangles and whole rows with the same square-bracket syntax you use for any NumPy array. The surprise is that a rectangle taken this way is a *window onto the same memory*, not a separate copy.

**Precise version.** For an array `a`, the expression `a[r, c]` returns one pixel, `a[r0:r1, c0:c1]` returns the sub-block of rows $r_0, \dots, r_1 - 1$ and columns $c_0, \dots, c_1 - 1$ (the end index is excluded), and a step such as `a[::2, ::2]` keeps every second row and column. All of these are **views**: new array objects that share the original's memory. Changing a view changes the original. Boolean masks and index lists create copies instead. Calling `.copy()` makes a copy explicitly.

```python
r, c = 100, 200
print(gray[r, c])             # row first, then column
print(rgb[r, c])              # three numbers: R, G, B
patch = gray[100:108, 200:208]            # rows 100..107, columns 200..207
print(patch.shape, np.shares_memory(patch, gray))

work = gray.copy()
work[100:108, 200:208] = 0                # writing through a slice edits `work`
print(work[100:108, 200:208].max(), gray[100:108, 200:208].max())

H, W = gray.shape
vec = gray.reshape(-1)                    # flatten: row-major order
print(vec.shape, vec[r * W + c] == gray[r, c], np.shares_memory(vec, gray))
print(np.array_equal(gray[::-1], np.flipud(gray)), gray[:, ::-1].shape)
mask = gray > 200
print(mask.dtype, mask.sum())
```

Output:

```text
54
[81 57 17]
(8, 8) True
0 109
(262144,) True True
True (512, 512)
bool 55112
```

What each line shows:

- `gray[100, 200]` is 54 and `rgb[100, 200]` is `[81 57 17]`: a color pixel is a short vector, one number per channel.
- The 8 × 8 patch shares memory with `gray`, so it is a view. Because `work` is a copy of `gray`, zeroing a patch of `work` leaves `gray` untouched (its patch still has maximum 109). If you had written to the view of `gray` itself, the original photo would have changed.
- Flattening gives a vector of $HW = 262144$ numbers in which pixel $(r, c)$ sits at position $rW + c$. This flattened form is the input vector that classical classifiers and the first layer of a fully connected network see (see [ML 01a](/en/learn/ml/ml-01a-linear-algebra/) and [ML 01](/en/learn/ml/ml-01-introduction/)).
- Flipping the image upside down is `gray[::-1]`, a view with a negative row step; no loop is needed. The comparison with `np.flipud` is `True`.
- A comparison such as `gray > 200` yields a boolean array of the same shape, here with 55,112 `True` entries. Boolean masks are how you select, count or edit pixels that satisfy a condition.

## Color images and channel order

**Plain version.** A color image stores three numbers per pixel, one for how red, one for how green and one for how blue. The trouble is that two common conventions order these three numbers differently, and nothing in the array tells you which one you have.

**Precise version.** Most Python imaging code (NumPy arrays from scikit-image [6], Matplotlib, Pillow) uses the order red, green, blue (**RGB**). OpenCV's `imread` returns **BGR**: blue is channel 0 and red is channel 2. Mixing the two does not raise an error; it silently swaps red and blue, so skin looks blue and the sky looks orange. To make the effect visible without a file on disk, the code below writes the color test image to a temporary PNG, reads it back with OpenCV and compares.

```python
import pathlib, tempfile
import cv2
from skimage import io

with tempfile.TemporaryDirectory() as d:
    path = pathlib.Path(d) / "astronaut.png"
    io.imsave(path, rgb)                   # a PNG written in R, G, B order
    bgr = cv2.imread(str(path))            # OpenCV hands the channels back as B, G, R
print(rgb[100, 200], bgr[100, 200])
print(np.array_equal(bgr[..., ::-1], rgb))
print(np.array_equal(cv2.cvtColor(bgr, cv2.COLOR_BGR2RGB), rgb))

weights = np.array([0.299, 0.587, 0.114])
manual = rgb @ weights                     # weighted sum of R, G, B -> float64 (H, W)
cv_gray = cv2.cvtColor(rgb, cv2.COLOR_RGB2GRAY)
print(cv_gray.dtype, np.abs(manual - cv_gray).max())
from skimage.color import rgb2gray
print(np.abs(rgb2gray(rgb) * 255 - cv_gray).max())
```

Output:

```text
[81 57 17] [17 57 81]
True
True
uint8 0.5010000000000332
15.529299999999992
```

The same pixel reads `[81 57 17]` as RGB and `[17 57 81]` as BGR. Reversing the last axis, `bgr[..., ::-1]`, is a free way to flip the order, and `cv2.cvtColor` with `COLOR_BGR2RGB` does the same thing explicitly. Both restore the original exactly.

To turn color into gray, the standard approach is a **weighted sum** of the channels, because the eye is more sensitive to green than to blue. The weights $0.299, 0.587, 0.114$ come from the luma definition in the ITU-R BT.601 television standard [8, Sec. 2.5.1], and the check above shows OpenCV's gray conversion agrees with that weighted sum to within 0.501 gray level, which is just rounding to integers. Different libraries use different weights: scikit-image's `rgb2gray` differs from OpenCV's result by up to about 15.5 gray levels on this image. So never assume that "gray" means the same numbers across libraries. Compare against the documentation of the function you call.

## Data types and the wraparound trap

**Plain version.** The most common storage type for images is the 8-bit unsigned integer, which can only hold 0 to 255. If a calculation goes past 255 it does not stop at 255: it silently starts again from 0. A pixel that was almost white can become almost black.

**Precise version.** For an unsigned integer type `uint8`, arithmetic is performed modulo $2^8 = 256$. So $250 + 10 = 260 \equiv 4$ and $250 - 251 = -1 \equiv 255$. Because values are not saturated, brightening or subtracting images in `uint8` is unsafe. NumPy 2 also refuses to combine an array with a Python integer that does not fit the array's type: it raises an error instead of quietly widening, following NEP 50 [5]. The safe recipe has three steps: convert to a wider type (`int16`, `float32`), compute, then clip back to the valid range and convert back to `uint8`.

```python
from skimage.util import img_as_float

a = np.array([250], dtype=np.uint8)
print(a + 10, a - 251, a.astype(np.int16) + 10)
try:
    a + 300
except OverflowError as e:
    print("OverflowError:", e)

wrapped = gray + np.uint8(60)
clipped = np.clip(gray.astype(np.int16) + 60, 0, 255).astype(np.uint8)
print((gray >= 196).sum(), (wrapped < gray).sum(), clipped.max())

x = gray.astype(np.float32) / 255.0
print(x.dtype, x.min(), x.max(), np.allclose(x, img_as_float(gray)))
y = np.clip(1.2 * x, 0, 1)
out = np.round(y * 255).astype(np.uint8)
print(out.dtype, out.max())
```

Output:

```text
[4] [255] [260]
OverflowError: Python integer 300 out of bounds for uint8
72087 72087 255
float32 0.0 1.0 True
uint8 255
```

Reading it: in `uint8`, `250 + 10` gives 4 and `250 - 251` gives 255, while in `int16` the sum is a correct 260. Adding 60 to every pixel wraps exactly the pixels whose value is at least $196$ (since $196 + 60 = 256$): there are 72,087 of them, and the same 72,087 pixels come out *darker* than they went in. The clipped version keeps all of them at the maximum 255 instead. The last block shows the usual float workflow: divide by 255 to work in $[0, 1]$, compute, clip, multiply back and round. `skimage.util.img_as_float` performs the same rescaling for `uint8` images.

<Figure src={overflow} alt="Four panels. The original grayscale photo; the photo after adding 60 in uint8, where the bright sky has turned black; the photo after adding 60 with clipping, where the sky is saturated white; and a plot of output versus input showing the wrapping curve dropping to zero at input 196 and the clipped curve staying at 255." caption="Figure 3 — Brightening by 60 levels. In uint8 the bright sky wraps around to black (orange curve). Converting to a wider type, adding, and clipping saturates it to white instead (green curve)." />

<Callout type="warn" title="Choose the dtype before the arithmetic">
Casting after an overflow cannot recover the lost value. Decide the working type first: `float32` in $[0, 1]$ for filtering and learning, `int16` for exact integer differences, and convert back to `uint8` only for saving or display. OpenCV's own arithmetic helpers such as `cv2.add` saturate instead of wrapping, but NumPy's `+` operator does not, so know which one a line of code is using. You can reproduce the effect on one color pixel in the [Playground](/en/playground/) experiment "When brightening makes a pixel darker".
</Callout>

## Sampling and quantization on a real image

**Plain version.** Two independent knobs control how much of the scene survives: the number of pixels (spatial resolution) and the number of gray levels (brightness resolution). Turning down the first makes the picture blocky; turning down the second makes smooth shading break into flat bands.

**Precise version.** Keeping every $s$-th row and column, `gray[::s, ::s]`, reduces an $H \times W$ image to about $H/s \times W/s$ samples. Done without smoothing first, this can create **aliasing**: fine detail that the coarser grid cannot represent shows up as false patterns instead of disappearing (the formal treatment is in [IP 02](/en/learn/image-processing/dip-02-fundamentals/) and the frequency-domain chapters). Reducing the bit depth from 8 to $b$ keeps only $2^b$ distinct values. The helper below rounds each pixel to the center of its bin, so with 4 bits there are 16 allowed gray levels.

```python
def quantize(img, bits):
    step = 256 // 2 ** bits
    return (img // step) * step + step // 2    # replace each bin by its center

for bits in (8, 4, 2, 1):
    print(bits, len(np.unique(quantize(gray, bits))))

small = gray[::4, ::4]                          # keep every 4th row and column
print(gray.shape, "->", small.shape, small.nbytes, gray.nbytes)

def invert_loop(img):
    out = np.empty_like(img)
    for r in range(img.shape[0]):
        for c in range(img.shape[1]):
            out[r, c] = 255 - img[r, c]
    return out

print(np.array_equal(invert_loop(gray), 255 - gray))
chw = np.transpose(rgb, (2, 0, 1))
print(rgb.shape, "->", chw.shape, np.shares_memory(chw, rgb))
print(np.mean(rgb, axis=(0, 1)))
```

Output:

```text
8 256
4 16
2 4
1 2
(512, 512) -> (128, 128) 16384 262144
True
(512, 512, 3) -> (3, 512, 512) True
[141.56249237 105.75944519  96.47507477]
```

The number of distinct values falls as $2^b$. Keeping every 4th row and column shrinks the image from 262,144 bytes to 16,384, one sixteenth of the memory. The nested loop and the single expression `255 - gray` give identical results (`True`), but the array expression runs as one compiled operation rather than a quarter of a million Python steps: write image code as array expressions whenever you can, and keep explicit loops for checking. Transposing to channels-first, `(3, 512, 512)`, is another view, which is the layout most deep-learning libraries expect. The last line, a mean over both spatial axes, gives one average per color channel.

Eight bits per channel is usually enough to show an image, but not always enough to process one: stretching the contrast of a dark, banded image only magnifies the bands. That is why image formats and sensors with more bits per channel exist, and why processing pipelines convert to floating point for the arithmetic. You can explore both knobs together in the [Playground](/en/playground/) experiment "Sampling and gray levels".

## A short checklist before you process an image

| Check | Why | One line |
| --- | --- | --- |
| Print `shape` and `dtype` | Confirms grayscale versus color and the value range | `print(a.shape, a.dtype, a.min(), a.max())` |
| Know the channel order | RGB and BGR look similar until the colors are wrong | `rgb = bgr[..., ::-1]` |
| Choose the working dtype | `uint8` wraps; `float32` in $[0, 1]$ is safe for filtering | `x = a.astype(np.float32) / 255` |
| Copy before editing | Slices are views and edits write through | `b = a.copy()` |
| Clip before converting back | Out-of-range floats become garbage in `uint8` | `np.clip(y, 0, 1)` |
| Remember `[row, column]` | Pairs from graphics APIs are `(x, y)` | `a[y, x]` |

## Modern view

Nothing in this chapter is obsolete, because deep-learning frameworks treat an image as a tensor and tensors behave like NumPy arrays. What changes is the *layout*, the *normalization* and, in recent research, the idea of what an image is.

**Tensors and layout.** A training batch adds a leading axis, giving `(N, H, W, C)` or the channels-first `(N, C, H, W)` that many libraries expect, as in the `np.transpose` view above. The pixel values are usually converted to `float32` and normalized, for example by dividing by 255 and standardizing each channel. All the pitfalls above carry over unchanged: a model trained on RGB input and fed BGR will silently degrade, and a preprocessing step that wraps in `uint8` can poison a whole dataset without raising an error. The convolution and Transformer chapters build directly on this view: [ML 03](/en/learn/ml/ml-03-convolutional-networks/) and [ML 04](/en/learn/ml/ml-04-vision-transformers/).

**Images as sequences of patches.** The Vision Transformer of Dosovitskiy et al. [10] (ICLR 2021) cuts an image into a grid of fixed-size patches, flattens each patch into a vector with the reshaping used in this chapter, and feeds the sequence to a standard Transformer. The paper reports that such a model, with large-scale pre-training, can match or exceed convolutional networks on image classification benchmarks while needing less training compute. The key point for this chapter is that the array operations (slicing into blocks, reshaping, transposing) *are* the model's front end.

**Images as functions.** A second modern idea replaces the grid with a learned function. Sitzmann et al. [11] (NeurIPS 2020) propose sinusoidal representation networks, small networks with periodic activations that take coordinates $(r, c)$ as input and return the pixel value, and show that they can represent images, audio, video and their derivatives in detail. Essakine et al. [12] (TMLR 2025) survey this *implicit neural representation* field: they propose a taxonomy over four groups of methods (activation functions, position encoding, combined strategies and network-structure optimization), compare them experimentally, and conclude with open problems such as more expressive activation functions, better position encodings and scalability to high-dimensional data. The array is still how such models are trained and evaluated, since the network is fitted to sampled pixels; but resolution becomes a property of how you query the function, not of the stored table.

**What is still open and what is not.** Questions that remain unsettled include how to store high-dynamic-range and wide-gamut color consistently across tools, and how learned representations should be compared with plain arrays at the same storage cost. Questions that are settled, and worth drilling until they are automatic, are the ones in this chapter: shape, dtype, channel order, views versus copies, and the habit of choosing the arithmetic type before computing.

## Key takeaways

- A digital image is a sampled, quantized signal stored as an array of shape `(H, W)` or `(H, W, C)`; $I[r, c]$ means row $r$, column $c$.
- `shape`, `dtype` and `strides` describe the array. A $512 \times 512$ 8-bit grayscale image holds 262,144 bytes; the color version holds three times as many.
- Slicing returns views that share memory with the original. Use `.copy()` before editing, and use array expressions rather than pixel loops.
- Libraries disagree on channel order (OpenCV uses BGR, most others RGB) and on the weights used for gray conversion; check, do not assume.
- `uint8` arithmetic wraps modulo 256. Convert to `int16` or `float32`, compute, clip, and only then convert back.
- Spatial resolution and gray-level resolution are separate choices, and reducing either loses information in a different way: blockiness and aliasing versus banding.
- Deep-learning tensors, image patches and implicit neural representations are all built on the same array view of an image.

<details>
<summary>Hint</summary>

With $A = 10$ and $B = 20$ in `uint8`, `A - B` equals $246$, not $10$. A safe version is `np.abs(A.astype(np.int16) - B.astype(np.int16)).astype(np.uint8)`.

</details>

5. **Design a bit-depth budget.** A grayscale image is stored with 8 bits, then quantized to $b$ bits. Predict the number of distinct values and the memory needed if each pixel is packed to exactly $b$ bits, for $b = 4$ and $b = 2$ at $512 \times 512$. Why does the picture in Figure 4 show bands at 4 bits but not at 8?

<details>
<summary>Hint</summary>

There are $2^b$ values: 16 and 4. Packed storage is $512 \times 512 \times b / 8$ bytes, which is 131,072 bytes at 4 bits and 65,536 bytes at 2 bits. Bands appear where a smooth gradient crosses a boundary between two bins: at 8 bits the steps are 1 gray level, below what the eye can distinguish on most displays, while at 4 bits they are 16 levels apart.

</details>
