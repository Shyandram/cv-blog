先想工作在哪裡發生。編輯器裡的 agent、固定排程的助理，以及嵌入自己產品的開發框架，對應不同操作方式。選模型，只是選工具的一部分。

這篇接續 [agent 基礎系列](/zh-tw/blog/agents-from-prompts-to-systems/)。產品與儲存庫來源於 **2026 年 11 月 5 日**查核，以下比較文件記載的設計與部署選項，不是實測速度排名，也不宣稱這些就是全部主流產品。

## 分開看工具、模型與服務

開源用戶端可以呼叫閉源模型；開放權重模型可以透過付費 API 使用；能下載的應用程式，也可能將提示送到遠端。應分別問：工具程式碼能否查看與修改？模型權重能否取得並自行執行？接收資料的基礎設施由誰操作？

例如 Codex CLI 儲存庫採 Apache-2.0，但選定模型的供應方式與條款是另一件事。OpenHands 有公開開發平台，各種部署形式也應個別檢查。這些事實都不代表所有相關服務能在本地執行，或完全免費。[1, 6]

## 主流 coding agent 工具

| 工具 | 文件記載的使用形式 | 要分清楚的開放範圍 | 適合的第一次試用 |
| --- | --- | --- | --- |
| Codex CLI | 終端中的 coding agent | Apache-2.0 用戶端；模型與託管服務另有條款 [1] | 有可執行測試的小型修補 |
| Claude Code | 終端與支援整合中的開發流程 | 專有產品；公開文件不等於開放模型權重 [2] | 依儲存庫指引完成跨檔案修改 |
| Cursor | 編輯器、agent 與雲端工作介面 | 專有應用與服務；確認選定模型及執行位置 [3] | 修改功能、看差異，再互動調整 |
| GitHub Copilot | GitHub 上的儲存庫問答、修改規劃與審閱 | 託管產品，使用權依帳號而定 [4] | 最終交付為 PR 的明確 issue |
| Gemini CLI | 終端 agent | Apache-2.0 用戶端；模型供應商存取另計 [5] | 讀取本地檔案並使用已授權工具 |
| OpenHands | Agent 開發與軟體工作平台 | 核心儲存庫公開；檢查部署方式及額外條款 [6] | 在可重現的隔離工作區完成任務 |
| Aider | 搭配本地或雲端模型的終端結對開發 | Apache-2.0 工具；模型另有條款 [7] | 每次都能審閱的小範圍修改 |
| OpenCode | 可選模型供應商的 coding agent 介面 | MIT 工具；供應商與服務條款另計 [8] | 用兩種支援的模型設定重跑同一任務 |
| Cline | SDK、編輯器擴充與 CLI 助手 | 查看公開儲存庫與該版本授權 [9] | 工具行動與核准過程容易檢查的修改 |

第一次試用應縮小自己的真實工作。保持起始版本、任務文字、測試指令與允許行動一致，查看修補內容、無關修改、指令失敗後的恢復，以及需要多少監督。如果介面能讓你更早發現錯誤，它可能比一點評測分數差距更重要。

## 需要自己開發應用程式時

如果要自行掌控狀態轉換、工具 API、評估或產品介面，才更需要框架。框架帶來額外工程責任，不會替你定義成功。

| 工具類型 | 提供什麼 | 仍需自行設計什麼 |
| --- | --- | --- |
| LangGraph | 有狀態的 agent／流程協調與持久化 [10] | 狀態結構、重播行為、任務檢查 |
| OpenAI Agents SDK | Agent、工具、交接與追蹤等基本組件 [11] | 業務邏輯、憑證邊界、驗收測試 |
| CrewAI | Agent／任務協調與工作流程結構 [12] | 有用的工作拆分與整合品質 |
| Browser Use | 瀏覽器 agent 函式庫，另有託管服務 [13] | 任務範圍、登入狀態與行動後檢查 |
| n8n | 結合 AI 能力的視覺化流程自動化 [14] | 觸發規則、錯誤路徑、資料約定與交付 |
| OpenClaw | 通道、工作階段、工作區工具與個人 agent 操作 [15] | 具體程序、執行政策與維運方式 |

n8n 將自己描述為 **fair-code**，不能把看得到儲存庫、能自行部署，直接等同不受限制的開源授權。同樣地，已經有可靠 API 的操作，也不必只因為有瀏覽器函式庫，就改用畫面操作。[13, 14]

## 依自己的情境選擇

想邊看邊改善程式，先選一個編輯器或終端 agent。想交辦範圍明確的 issue，就測試儲存庫／雲端流程並檢查變更。目標是跨通道的固定個人任務，可以研究 OpenClaw 的操作模式。Agent 是產品的一部分時，先從小型 SDK 或明確流程開始，任務需要時再加入持久化。

不寫程式的使用者，可以從既有產品支援的介面與可回復任務開始。開發者可以先做好單一工具呼叫與結果驗證，再加入多 agent 結構。團隊試用時則應把帳號管理、稽核與恢復一起納入，不只比較最漂亮的展示。

這些是選型原則。編輯器、終端用戶端與託管工作者即使使用相同模型，情境整理、權限、工具與檢查仍可能不同。最後表現的是整個系統。

## 做一個小而公平的比較

準備三種任務：一般成功案例、應該先釐清的模糊請求，以及刻意製造工具失敗的任務。程式工作再加入既有迴歸測試，以及會抓到不完整修補的案例。模型不具確定性時，每個候選都應多跑幾次。

記錄應用與模型確切版本、起始檔案、啟用工具、額度、產物、測試、耗時與人工修正。訂閱或基礎設施成本會影響使用時，也一起記錄。比較的是**每個通過驗收成果的成本**，不只 token 速度或單次呼叫價格。指標的含義可接著看[模型與評測指南](/zh-tw/blog/models-benchmarks-and-people/)。

試用時不必裝滿所有連接器。先加入工作需要的工具，確認 agent 能找到並正確使用。工具清單變長，也可能增加選擇歧義，讓失敗更難追蹤。

## 決定長期使用之前

確認能否匯出產物與有用的任務歷史、重現環境、理解模型／供應商路由，以及服務不可用時能否繼續工作。自行部署時，成本應包含升級、依賴、必要 GPU 容量與故障排查。本地執行帶來控制權，也帶來維運工作。

選擇能在代表性任務上，減少不可接受失敗、且監督負擔合理的候選。把試用案例保留下來，下一次模型或產品更新時，它們就是你的迴歸測試。

選好工具後，接著設計 [Agent 工作流程](/zh-tw/blog/agent-workflows/)：定義成果、安排有界限的步驟、檢查證據，並處理失敗恢復。
