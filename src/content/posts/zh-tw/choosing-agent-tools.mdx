先想工作在哪裡發生。編輯器裡的 agent，與固定排程的助理，或嵌入自己產品的框架，各自支援不同的工作方式。選模型只是選工具的一部分：同一個模型，會因為工具如何組成情境、允許哪些行動、如何檢查結果，而有不同的表現。

這篇接續 [agent 基礎系列](/zh-tw/blog/agents-from-prompts-to-systems/)。正文是不針對特定產品的決策框架；具名的產品、授權與使用形式，在[現行選項](#現行選項查核日期-2026-年-11-月-6-日)。它描述的是文件記載的設計選擇，不是實測的速度排名。

## 重點

- 先替工具分類：互動式（編輯器、終端）、委派式（回傳 pull request 的雲端工作者）、常駐式（依排程運行的個人助理）、嵌入式（在你產品中的 SDK 或框架），或編排式（工作流程自動化）。
- 分開問三個關於開放程度的問題：我能檢視並修改工具的程式碼嗎？我能自己執行模型嗎？接收我資料的服務由誰營運？
- 決定性的差異往往不是模型：情境的組成方式、權限模型、執行位置、審閱介面，以及失敗後的復原。
- 用固定的流程，在你自己的小型任務上比較候選工具，並以每個通過驗收的成果所花的成本計分，而不是每次呼叫的價格。
- 投入之前先確認退出途徑：能否匯出輸出與歷史、環境能否重現，以及服務無法使用時會怎樣。

## 五類 agent 工具

| 類型 | 在哪裡運行、如何互動 | 最適合 | 要管理的主要風險 |
| --- | --- | --- | --- |
| 互動式編輯器或終端 agent | 在你的機器或開發機上；你觀看並引導每一步 | 你想留在循環中，隨時審閱出現的 diff | 沒讀就核准行動 |
| 委派式雲端工作者 | 在供應商的環境中；回傳分支或 pull request | 範圍明確、測試完善的 issue | 通過測試卻偏離意圖的變更 |
| 常駐式個人助理 | 連接聊天通道與排程的長時間運行服務 | 跨應用程式的週期性個人任務 | 過大的憑證；讀取的內容中夾帶注入的指令 |
| 嵌入式 SDK 或框架 | 在你自己的應用程式內 | Agent 是你產品的一部分 | 狀態、評估與維運都要自己負責 |
| 工作流程自動化平台 | 視覺化或宣告式的流程，其中有模型步驟 | 步驟大多固定，只有少數需要判斷 | 錯誤路徑中的無聲失敗 |

非工程背景的人，通常應該從既有應用程式支援的介面，搭配可以還原的任務開始。開發者應該先用一個工具，做出一個可驗證的成果，再加入多個 agent。團隊在試用時，應把帳號管理、稽核日誌與復原一併納入，而不是只評估最漂亮的示範。

## 分開看工具、模型與服務

開源用戶端可以呼叫閉源的託管模型；開放權重的模型可以透過付費 API 提供；可以下載的應用程式，仍可能把提示送到遠端服務。請分開問三個問題：

1. **程式碼：** 我能閱讀、修改並重新散布這個工具嗎？請查看儲存庫的授權檔，而不是行銷頁面。有些專案採用標準的開源授權；有些採用附帶商業限制的「原始碼可得（source-available）」或「fair-code」授權；也有些把部分程式碼放在另外的企業授權之下。[1, 12]
2. **模型：** 這個工具能使用哪些模型？我能自備模型嗎？其中有任何一個能在本機執行嗎？
3. **服務：** 哪些基礎設施會接收我的檔案與提示？保留什麼？條款是什麼？

[選擇模型](/zh-tw/blog/models-benchmarks-and-people/#開放程度是每一層各自的屬性)詳細說明了這些授權層次，包括權重授權，以及開源與開放權重的差別。

## 工具之間真正的差異

當兩個工具使用同一個模型，結果仍會因為外圍的機制而不同：

| 面向 | 要問的問題 | 為什麼重要 |
| --- | --- | --- |
| 情境組成 | 它如何找到相關的檔案、文件與歷史？會讀取專案指令檔嗎？ | 多數錯誤修改都來自缺少或錯誤的情境 |
| 工具與權限模型 | 哪些行動需要核准？我能允許唯讀工具，並限制寫入嗎？ | 決定錯誤最多能造成多大的損害 |
| 執行位置 | 本機 shell、容器、遠端虛擬機，還是供應商的雲端？ | 決定資料暴露程度與可重現性 |
| 審閱介面 | 在接受之前，我能看到每個 diff、指令與來源嗎？ | 你只能抓出自己看得到的錯誤 |
| 可擴充性 | 支援 skills、MCP 伺服器或自訂工具嗎？ | 讓你加入自己的程序，而不是反覆重新說明 |
| 復原 | 當機後能續作、復原變更，或在新的工作階段中繼續嗎？ | 長任務會在中途失敗；復原能力決定成本 |
| 可觀測性與稽核 | 行動是否以團隊能審閱的形式記錄？ | 共用或受監管的工作必備 |

對程式碼工作來說，第一列與第四列通常最重要：一個能清楚呈現 diff 並執行你的測試的工具，比一個模型略強、介面卻不透明的工具更安全。

## 做一個小而公平的比較

從你的實際工作中挑三到五個任務：一個普通的成功案例、一個應該引出釐清問題的模糊請求，以及一個刻意設置工具失敗的任務（缺少相依套件、測試失敗）。若是程式碼，加入一個既有的迴歸測試，以及一個能抓出不完整修補的案例。每個候選工具都要執行不只一次，因為模型輸出會變動。

在所有候選工具之間，固定這些條件：起始版本、任務文字、測試指令、允許的行動與預算。每次嘗試都記錄：

- 確切的應用程式與模型版本，以及啟用的工具；
- 對照*在試用之前*就寫好的驗收檢查，通過或失敗；
- 不相關的變更，以及從失敗中復原是否成功；
- 耗費時間、人工介入與修正的次數；
- 花費，包含適用時的訂閱費或基礎設施費用。

然後比較**每個通過驗收的成果的成本**：總花費除以通過的輸出數量。一個便宜、卻需要三次嘗試加手動修補的工具，成本可能高過一次就通過的昂貴工具。[模型評估指南](/zh-tw/blog/models-benchmarks-and-people/)說明了如何閱讀通過率，以及小樣本下的不確定性。

試用時不要安裝所有可用的連接器。只加入任務需要的，並確認 agent 能使用它們；工具清單過長會造成選擇上的含糊，也讓失敗更難追查。

## 投入之前

- **退出：** 你能把輸出、歷史與設定匯出成可用的格式嗎？
- **可重現性：** 同事能否依儲存庫裡的檔案重建環境？
- **路由：** 你知道每個請求由哪個供應商與模型處理嗎？能固定版本嗎？
- **持續性：** 當你依賴的服務或模型無法使用或停用時，會怎樣？
- **自行架設的成本：** 納入升級、相依套件、GPU 容量與事件處理，而不只是授權。

選擇能以最少不可接受的失敗與可負擔的監督，完成你代表性任務的候選工具。保留這些試用任務：下一個版本釋出時，它們就是你的迴歸測試集。然後再圍繞這個工具設計[工作流程](/zh-tw/blog/agent-workflows/)。

## 現行選項，查核日期 2026 年 11 月 6 日

下表是具代表性的例子，不是完整的市場調查，也不是排名。授權是在查核日期讀取各儲存庫的授權檔；託管服務的條款另當別論，且可能改變。

**Coding agents**

| 工具 | 類型 | 程式碼授權或狀態 | 值得先試的第一個任務 |
| --- | --- | --- | --- |
| Codex CLI | 終端 agent | Apache-2.0 用戶端；模型存取與服務條款另計 [2] | 有可執行測試的小型儲存庫修補 |
| Claude Code | 在終端、IDE 擴充套件、桌面應用程式與網頁中的 agent | 專有產品 [3] | 依儲存庫指引完成的跨檔案修改 |
| Cursor | 具備 agent 模式的 AI 程式碼編輯器 | 專有的應用程式與服務 [4] | 編輯、檢查 diff 並修訂一個功能 |
| GitHub Copilot | 在 GitHub.com 上：儲存庫聊天、會開 pull request 的背景 agent，以及程式碼審查 | 託管產品，存取權依帳號而定 [5] | 成果為 pull request 的一個有範圍的 issue |
| Gemini CLI | 終端 agent | Apache-2.0 用戶端；供應商存取另計 [6] | 讀取本機檔案並使用一個已核准工具的任務 |
| OpenHands | Agent 平台；預設在本機，可選擇雲端 | MIT 授權的儲存庫 [7] | 在隔離的容器工作區中執行的任務 |
| Aider | 終端中的結對程式設計工具 | Apache-2.0 [8] | 你逐一審閱每個修補的小範圍變更 |
| OpenCode | 支援多家供應商的終端 agent | MIT [9] | 用兩種不同的模型設定執行同一個任務 |
| Cline | 編輯器擴充套件、CLI 與 SDK | Apache-2.0 [10] | 每個工具動作都顯眼地等待核准的變更 |

**框架與自動化**

| 工具 | 提供什麼 | 程式碼授權 | 你仍須設計什麼 |
| --- | --- | --- | --- |
| LangGraph | 具持久化的有狀態圖形編排 | MIT [11] | 狀態 schema、重播行為、任務檢查 |
| OpenAI Agents SDK | Agents、工具、handoff、追蹤 | MIT [13] | 業務邏輯、憑證邊界、驗收測試 |
| CrewAI | 多 agent 任務編排 | MIT [14] | 真正有幫助的分工方式 |
| Browser Use | 瀏覽器自動化 agent 函式庫（另有託管服務） | MIT [15] | 身分驗證的處理，以及行動後的檢查 |
| n8n | 含 AI 步驟的視覺化工作流程自動化 | Sustainable Use License（「fair-code」）；企業檔案採另外的授權 [12] | 觸發條件、錯誤路徑、資料約定、寄送 |
| OpenClaw | 常駐式個人 agent gateway：通道、工作階段、排程 | MIT [16] | 程序、執行政策、維運慣例（[第三篇](/zh-tw/blog/openclaw-practical-agent-operations/)） |

如果一項操作已有可靠的 API，就不該因為有瀏覽器自動化函式庫，而去操作網頁；優先使用 API，瀏覽器只用在只有介面才提供的功能上。

## 延伸閱讀

- Anthropic, [*Building effective agents*](https://www.anthropic.com/research/building-effective-agents)：什麼時候才需要 agent，什麼時候工作流程就夠了。[17]
- Anthropic, [*Writing effective tools for AI agents*](https://www.anthropic.com/research/writing-tools-for-agents)：什麼樣的工具讓模型容易正確使用，評估工具內建的行動時很有幫助。[18]
- Open Source Initiative, [*The Open Source Definition*](https://opensource.org/osd)：程式碼授權中「開源」意義的依據。[1]
- 各工具自己的授權檔（連結在表格中）：回答「它是開放的嗎？」唯一可靠的來源。
