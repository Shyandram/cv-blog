聊天助手可以告訴你如何修正失效連結。Agent 則可以查看儲存庫、找出正確目標、修改連結、執行檢查，再交出可供審閱的變更。真正有用的差別，在於它能觀察執行結果，再決定下一步。

這個三篇系列沿著這個循環，從日常使用一路走到開發與維運。**如果你用過聊天機器人，卻還沒開發過 agent，可以從這篇開始。** 只需要對檔案與指令有基本認識，不必先學會訓練語言模型。

## 先說清楚想完成什麼

以每週論文摘要為例。有用的成果是一份本地文件，包含每篇選定論文的簡短說明、原始來源連結，以及仍不確定的地方。「研究所有 agent 技術」沒有界定搜尋範圍，也沒有完成標準。「根據這些來源整理摘要，寄出前先停下」才是一個可以完成的任務。

寫程式也是如此。說明可以觀察的行為、允許修改的檔案、驗證指令，以及預期交付的產物。計畫的價值在於減少不確定性；計畫寫得很長，本身不代表工作已經推進。

以下是可以自行調整的任務範本：

```text
Goal: prepare a short digest of the three supplied papers.
Inputs: the supplied PDFs and their official publication pages.
Output: a local draft with a claim, evidence, limitation, and source for each.
Allowed actions: read these sources and write inside the draft directory.
Acceptance: every factual claim has a source; unknowns remain explicit.
Stop: after the draft and source checks; do not send or publish it.
If blocked: preserve completed work and name the missing evidence.
```

它依序說明目標、輸入、輸出、允許的行動、驗收、停止條件，以及受阻時的處理方式。這是一份任務約定，不是神奇提示詞。真正的應用程式仍須透過工具限制檔案與寄送權限，單靠文字無法強制執行。既有授權可以持續有效；超出原本範圍的新行動，則需要另外處理。

第一次嘗試時，選擇產物小、容易檢查的工作，例如草稿、從指定文件整理的表格，或可重現錯誤的修補。要看實際產物與檢查結果；最後一句充滿自信的「完成了」，證據力很有限。

## 一個 agent 由哪些部分組成

**模型**提出行動。**工具**讓它讀取或改變環境。**情境（context）**提供目前任務與證據。**Harness** 是外圍的執行系統，管理循環、工具呼叫、狀態、限制與恢復。**Skill** 則封裝可重用的工作知識，讓執行系統在適當時機提供給模型。這些功能可以存在於同一個應用程式，但除錯時仍值得分開理解。[4, 5, 9]

假設摘要引用了錯誤論文，先找錯誤從哪裡進來。情境裡沒有正確來源？搜尋找到同名文章？工具截掉了關鍵段落？最後只檢查網址存在，沒有確認內容？這些原因需要不同修正。一直重寫系統提示詞，可能完全碰不到真正問題。

## 這些方法如何演進

下面的年份對應具代表性的論文與工程報告，不代表相關概念都在當年首次被發明。更早的規劃、軟體自動化與資訊檢索，都是這段發展的背景。

### 2022–2023：把語言接到行動與回饋

**ReAct** 交錯安排推理與行動，讓新的觀察可以改變下一步決定。它在問答與互動任務上的實驗，說明執行過程中取得資訊，為什麼可能比只依賴起始提示更有用。這不等於已證明一個不受限制的 agent 能可靠完成任意工作。[1]

**Toolformer** 研究如何透過自監督訓練，學會何時呼叫 API、如何填入參數。這與應用程式把工具定義交給已訓練好的模型，是不同層次的工作。替系統加一個計算機工具，並不等於重現 Toolformer 的訓練方法。[2]

**Reflexion** 在多次嘗試之間保留文字回饋，不更新模型權重。實務上可以聯想到：「前一個候選方案通過語法檢查，但漏掉空輸入。」這比「再努力一點」更具體，但回饋本身也可能錯誤。論文中的評估結果，不會讓自我批評自動成為獨立的正確性檢查。[3]

### 2024：工作流程成為架構選擇

Anthropic 的 *Building effective agents* 區分了預先定義的工作流程，以及由模型選擇下一步的系統。路由、平行工作、評估迴圈，成為依任務選擇的模式，而不是每個 agent 都必須具備的功能。[4]

「擷取這些欄位、驗證結構、產生報告」通常可以先用固定流程。「檢查失敗後，需要重新調查原因」才更需要動態循環。即使如此，外圍仍可以由確定性的程式掌控：模型提出修正，程式負責權限、測試與完成判斷。

### 2025：情境、可重用程序與長時間任務

任務變長後，關鍵變成哪些資訊能跨步驟保留下來。情境工程處理證據選擇、按需檢索，以及對話歷史的壓縮或外部保存。Skills 封裝可選擇載入的程序；長時間執行的 harness 實驗則加入初始化、漸進工作與跨工作階段的交接產物。[5–7]

這些機制處理不同問題。檢索找證據；壓縮縮短目前歷史；記憶跨任務保留選定資訊；檢查點記錄可恢復的執行狀態；skill 說明如何處理反覆出現的工作。把這五者全部叫作「記憶」，反而不容易找出問題。

### 2026：把環境與評估器納入核心設計

OpenAI 的 harness engineering 報告強調儲存庫知識、容易理解的環境，以及能由程式檢查的限制。Anthropic 的應用開發報告分開規劃、生成與評估；其受管理 agent 架構則分開工作階段歷史、harness 與執行環境。這些都是工程案例，不是適用所有任務的效能保證。[8–10]

值得保留的原則，是讓工作可以被檢查：下一次執行要能找到目標、目前檔案、尚未排除的失敗，以及已完成檢查的證據。模型更新時，也要重新測試外圍設計。為舊模型加入的補救機制，可能變成新模型不需要的負擔。[10]

## 選擇足以處理問題的最小系統

| 情境 | 建議起點 | 關鍵檢查 |
| --- | --- | --- |
| 解釋或改寫已提供的文字 | 單次模型呼叫 | 回答是否符合評分規準？ |
| 步驟與輸入格式固定 | 固定流程搭配驗證 | 中間資料與最終產物是否通過？ |
| 失敗後需要調查並改變策略 | 有界限的單一 agent 工具循環 | 能否處理代表性的失敗？ |
| 多項獨立調查可以整合 | 有清楚輸出約定的平行工作者 | 整合成果是否值得額外成本？ |
| 工作跨越重啟或外部事件 | 持久化工作階段與排程／事件驅動 | 能否續作而不重複產生副作用？ |

這張表是設計建議，不是效能排名。工作彼此獨立時，平行處理才容易帶來幫助。兩個 agent 同時修改同一份檔案，可能把時間花在處理彼此的衝突。獨立審閱者可以找出遺漏，但兩個模型也可能共享同一個錯誤假設。能使用可執行檢查或原始證據時，就讓它們參與判斷。[4, 9]

## 近年技巧的實用地圖

### 改善輸入，選擇真正需要的情境

先定義具體的輸出約定，提供一個有代表性的範例。下游程式需要解析欄位時，使用結構化輸出，同時驗證欄位內容與形狀。字串長得像日期，不代表它就是正確日期。

大型來源應檢索相關段落，保留穩定的來源位置。搜尋、開啟、檢查，再引用；搜尋摘要是線索，還不是最後證據。大型工具輸出可以放在提示之外，只回傳精簡結果與原始檔案位置。動態工具搜尋也採用相近思路，避免一開始就載入所有工具定義。[5, 11]

### 改善執行與恢復

工具要有清楚的參數型別、輸出上限、逾時與錯誤分類。暫時性的讀取失敗，應與不合法請求分開處理。寫入後若回應遺失，重試前要檢查實際狀態，或使用服務提供的冪等機制。逾時不代表事情沒有發生。

檢查點應包含目前任務、已驗證進度、剩餘工作、產物位置，以及辨識重播行動的識別碼。支援檢查點可以協助暫停與恢復，但對外部系統產生的副作用仍需要另外處理。例如 LangGraph 提供持久化檢查點，哪些動作能安全重播，仍由應用開發者決定。[12]

### 改善評估，讓更新有依據

保留一組小型迴歸案例，涵蓋一般成功情境、常見失敗與邊界條件。同時評估最終環境與對話：報告 agent 要交出可用報告，訂位 agent 要在系統裡留下正確訂位。除了品質，也記錄成本、耗時與人工介入。[13]

反思、提示詞最佳化與自動學得的 skills，都可以提出改善候選。**GEPA** 使用執行軌跡回饋演進提示詞；其比較結果依任務而定，不能直接推論提示詞最佳化永遠能取代模型訓練。用來調整程序的案例，應與最後判斷成效的案例分開。[14]

### 值得持續追蹤的新方向

**Recursive Language Models（RLMs）** 把長輸入當作可從外部檢查的環境，透過程式化操作與遞迴呼叫拆解內容。這與把更長文件直接塞進更大情境視窗不同。對自己的工作而言，應檢查額外控制流程能否在可接受成本下，提高證據涵蓋的完整性。[15]

程式化工具呼叫把篩選、迴圈與資料轉換交給程式，讓模型只接收真正需要的結果。它可以減少不必要的中間文字，但仍需要控制執行環境與資料存取。沒有資料整合需求時，直接呼叫一個工具通常更簡單。[11, 16]

其他持續發展的實務包括瀏覽器／電腦操作、事件驅動 agent、模型路由、提示快取，以及自動修訂工作程序。每項技巧都應對應一個已觀察到的瓶頸。例如必要操作只透過介面提供時，使用瀏覽器並確認點擊後的實際狀態；換成便宜模型前，先驗證分派給它的任務；使用快取時確認供應商的語意，不能把快取當成最新事實來源。

## Skills、MCP、ACP 與 A2A 處理不同層次

| 名稱 | 主要處理什麼 | 它本身不會直接提供什麼 |
| --- | --- | --- |
| Agent Skills | 可攜的任務指令與附屬檔案 | 新憑證或執行成功保證 |
| MCP | 應用程式與工具、情境來源的連接 | 任務計畫或完整 agent 執行系統 |
| ACP，此處指 Agent Client Protocol | 編輯器／用戶端與 coding agent 的通訊 | 適用所有行動的通用權限政策 |
| A2A | Agent 系統之間的通訊與任務協作 | 共享私有狀態或自動建立互信 |

這些區分依據各自的原始規格。它們是互補介面，不是同一種產品的四個競爭名稱。是否相容，仍須檢查兩端支援的版本與能力。[6, 17–19]

OpenClaw 位於應用與執行系統層，串接面向使用者的通道、工作階段、工具與工作區，是觀察這些需求如何結合的具體例子。[20] 不需要先導入每一種協定，才能把單一 agent 用好。

## 第一個值得做的實驗

選一件你已經知道如何檢查的工作。先跑簡單基準，再一次只改一個部分：加入相關 skill、改善工具錯誤訊息，或補上缺少的來源。比較產物品質，以及需要多少人工修正，並保存失敗案例。

以論文摘要來說，可以測試名稱模糊、PDF 缺失，以及新來源與舊摘要互相矛盾的情況。有用的行為是消除歧義或清楚指出缺口。如果證據不存在，把表格全部填滿也不算成功。

當你能說出預期產物、允許的行動、完成檢查與停止條件，就可以繼續讀[如何建立 skill 與小型 harness](/zh-tw/blog/agent-skills-and-harnesses/)。如果已經在使用 agent 執行系統，也可以直接看 [OpenClaw 實務](/zh-tw/blog/openclaw-practical-agent-operations/)。
