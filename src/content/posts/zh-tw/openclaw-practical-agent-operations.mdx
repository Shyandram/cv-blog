OpenClaw 讓 agent 的抽象組件變得具體：訊息從通道或介面進入，gateway 將它導向工作階段，執行系統再結合模型、工具與工作區資訊。它很適合用來學習如何操作與維運 agent，而不只是如何下提示詞。[1]

## 追蹤一個請求如何通過系統

**Gateway** 是串接通道、用戶端與執行操作的常駐服務。**工作階段（session）** 識別對話與執行歷史。**工作區（workspace）** 保存工作使用的檔案。**Skills** 提供程序，**工具**提供行動，已配對的 **node** 則可以暴露其他裝置的能力。即使都在同一臺電腦上，這些職責仍然不同。[1, 2]

回應失敗時，先定位在哪個階段。通道可能已連線，模型存取卻不可用；模型能回答，執行環境卻缺少必要指令；skill 已安裝，卻不符合目前 agent 的啟用條件。「機器人在線上」無法區分這些情況。

## 從一份本地草稿開始

沿用前兩篇的論文摘要任務。先使用一位使用者、一個工作區、一組模型連線與少量來源，產生本地草稿。等這條路徑通過，再加入訊息通道或固定排程。

官方快速入門涵蓋支援的執行環境、安裝方式、模型供應商設定、Gateway 狀態與 Control UI。需求會隨版本變動，安裝時應查看當前文件，不要照抄舊部落格中的執行環境版本。[3]

安裝預定使用的版本並完成初始設定後，下列文件記載的指令可查看狀態或開啟介面：

```bash
openclaw --version
openclaw gateway status
openclaw dashboard
openclaw skills list --eligible
openclaw skills check
openclaw security audit
```

`dashboard` 只負責開啟介面，不能驗證完整任務。`skills check` 協助發現缺少的先備條件。`security audit` 回報設定問題，不代表已證明每個外掛與工作流程都安全。這些指令不會安裝第三方 skill 或建立排程。[2–4]

把第一篇的摘要任務約定交給 agent，再查看真正的輸出檔案。確認論文身分一致、證據缺口清楚，而且沒有寄出內容。這次小型成功執行，會成為後續修改的比較基準。

## 加入一個你理解的 skill

一般本地工作區可以把[第二篇](/zh-tw/blog/agent-skills-and-harnesses/)的 `paper-digest/SKILL.md` 範例，放進該工作區的 `skills/` 目錄。固定版本文件中，工作區 skills 的優先序高於多種共享與內建來源。同名時，應確認實際選中哪個路徑。[2]

使用已安裝 CLI 的 skill 檢查指令，確認它已被找到且符合啟用條件。第一次測試明確要求使用 `paper-digest`；再試一般聊天請求，確認不會無差別套用這套程序。

安裝 skill，不代表它提到的每個依賴也都安裝了。如果行動在沙箱或已配對的 node 上執行，所需檔案、程式與憑證也必須在那個環境裡可用。只確認主機上有，還不夠。[2, 5]

### 分清楚這次更新的是哪一種 skill

固定來源版本中，一般檔案式 skill、受管理的函式庫版本，以及 Workshop 產生的 skill，更新規則並不相同。檔案式來源可以在變更後重新發現；受管理的選取項目保留指定版本，直到明確更新；Workshop 文件則說明，修改過的學得 skills 會在新工作階段載入。應確認使用的是哪個機制，不要假設每個執行中的工作階段立刻看到最新檔案。[2, 6]

為了讓測試能重現，記錄 skill 來源與版本，適當時開啟新工作階段，再跑相同驗收案例。第三方 skill 更新時，要檢查完整套件，包括腳本與參考檔案。簡短描述沒變，不代表工作程序也沒變。

## 讓記憶有用，也能被更正

目前記憶文件區分精簡的使用者資料、持久事實與決策，以及按日期保存的工作筆記。`USER.md` 放穩定偏好，`MEMORY.md` 放經整理的非個人資料，`memory/YYYY-MM-DD.md` 放日常觀察。實際載入方式仍依系統設定而定。[7]

對摘要專案來說，有用的持久筆記可以是「優先使用原始論文，標明無法取得的實驗」，並附上觀察日期。每篇論文的完整文字應保存在來源資料裡，不必全部塞進起始記憶。尚未確認的猜測，也不應悄悄變成永久事實。

偏好改變時，應替換被取代的舊規則，而不是追加互相矛盾的指令。證據與任務狀態也要分清楚：「星期二無法取得來源 B」不等於它永遠不可用。記憶檢索與一般搜尋一樣，都可能帶回過時資訊。

## 手動驗證後，再建立排程

固定摘要需要的不只是一個計時器。應定義時區、來源範圍、產物位置、重複處理政策、寄送對象、額度，以及缺少輸入時的行為。依真正需要的情境，決定使用既有或全新的工作階段。

**這裡有一項需要更新的遷移資訊：** 固定版本 OpenClaw 文件已將 heartbeat 監控描述為一般 automation jobs。主要管理介面是 `openclaw automations`，`openclaw cron` 則保留為別名。舊教學中設定 heartbeat 欄位的方式，可能對應較早版本。修改現有安裝前，先閱讀該版本的遷移文件。[8, 9]

新增工作前，先查看既有工作：

```bash
openclaw automations list --all
```

透過已安裝版本的管理介面建立只產生草稿的工作，查看定義，再檢查第一次執行。工作成功執行但無法送出結果，與工作根本沒有啟動，是不同失敗；執行與交付都要有紀錄。

為了控制重複產物，本系列建議替每份摘要指定穩定的期間識別，例如目標週次加上來源集合版本，並保存產物識別與交付紀錄。排程醒來兩次，不應直接變成發布兩份。這是應用設計建議，不代表某個設定旗標就能保證恰好一次交付。

## 分開處理存取、工具與執行環境

三個問題分別是：**誰可以提出請求、哪些行動可以執行、行動在哪裡執行。** 已配對的傳送者通過了存取檢查，但他請 agent 閱讀的網頁，不會因此取得下指令的權限。工具政策限制行動，沙箱限制部分執行環境。[4, 5]

固定版本的沙箱文件指出，沙箱預設未啟用；啟用後移動的是工具執行，Gateway 仍在主機上。不能只因產品名稱或 agent 有工作區，就推論它已在沙箱內，應確認實際生效的設定。[5]

OpenClaw 安全指引將一個 Gateway 視為一個信任邊界。多個 agent 或工作階段，本身不會替互不信任的對抗性使用者建立隔離。信任需求不同時，應分開憑證與執行邊界。[4]

論文摘要只需要取得來源與撰寫本地草稿。發布可以是對明確目的地執行的獨立授權操作。祕密值不要放進 skill 或產生的報告；檢查執行軌跡時，保留除錯所需資訊，但不要把憑證抄進可分享產物。

## 把學到的新程序當成可審閱變更

固定版本的 **Skill Workshop** 文件描述了可重用程序的保存、變更歷史、復原，以及供審閱背景學習結果的提案模式。這是 agent 改善工作指令的具體例子，不代表底層模型權重已經更新。[6]

有用的候選規則可以是：「PDF 取不到時，保留已驗證的中繼資料，並標示缺少的結果。」比較不好的規則是因一次成功，就學成「永遠相信這個網站」。應檢查規則範圍，用過去失敗案例比較，並保留回復方式。

接受新版本前，重新測試相關請求、不相關請求，以及曾經失敗的案例。如果新版本讓其他工作變差，就保留舊版。清楚的差異與通過的迴歸案例，比「agent 變聰明了」更有說服力。

## 從症狀開始排查

| 症狀 | 優先查看 | 避免什麼 |
| --- | --- | --- |
| 訊息沒有進入執行流程 | 通道存取、配對、路由與 Gateway 狀態 | 尚未確認傳遞就重寫 skill |
| 找不到 skill | 選定工作區、來源優先序、啟用條件 | 把安裝等同啟用 |
| 主機指令正常，任務裡卻失敗 | 真正執行主機、依賴與掛載檔案 | 為了缺少程式而全面放寬權限 |
| 一直出現舊指令 | 工作階段選取、skill 版本與更新規則 | 更新另一個同名副本 |
| 忘記了某個決策 | 已存記憶、載入限制與來源紀錄 | 每次把完整對話重新塞進提示 |
| 排程重複產生結果 | 執行歷史、觸發識別與應用紀錄 | 不確認狀態就重送 |

這些是排查假設，不是所有錯誤的標準答案。應用真實紀錄與生效設定確認；官方快速入門、skills、記憶與自動化文件，提供對應的檢查入口。[2, 3, 7, 8]

## 用可重複的驗收流程升級

記錄已安裝的應用、模型、skill 與外掛版本。遷移前依官方方式備份狀態，閱讀發布與遷移說明，能建立測試環境時先在其中升級，再跑同一個小型工作流程。更新文件區分套件／執行環境更新、狀態遷移與恢復程序。[10]

確認任務能啟動、選中預期 skill、建立草稿、來源仍可存取、記憶範圍正確，而且暫停後能續作。如果流程會寄送訊息，應在已授權的測試通道檢查目的地與重複行為。保留升級前狀態備份，依文件回復；只換回執行檔，不一定能撤銷資料結構遷移。

第一個專案可以停在有來源依據的本地摘要。當你能檢查產物、說明權限、重現失敗並恢復執行，就有基礎進一步建立固定運作的個人助理或更複雜的開發流程。
