模型只是工作系統的一個元件。排行榜能幫你縮小候選範圍，但工具、指令、資料與驗收條件，才決定它對你的工作是否有用。建議先讀 [Agent 工具怎麼選](/zh-tw/blog/choosing-agent-tools/)。

背景來源查核日期為 **2026 年 11 月 5 日**；下列版本與評測連結更新於 **2026 年 11 月 6 日**。這些是可進一步驗證的候選，不是完整模型清單，也不是我們重跑的效能排名。產品名稱、授權與可用性可能各自改變。

## 託管模型與開放權重

託管服務負責推論維運；你評估介面、資料保留設定、可用性與費用。可下載權重讓你決定在哪裡執行推論，同時也把記憶體、服務部署、升級與監測交給你。開放權重不代表訓練資料公開，也不代表授權沒有條件。

| --- | --- | --- |
| OpenAI：GPT、gpt-oss | 公司資料與 gpt-oss 儲存庫 [1, 2] | 託管 GPT 端點與可下載的 gpt-oss 是不同選項 |
| Anthropic：Claude | 公司與產品資料 [3] | 工具支援、情境處理、帳號條款及確切的託管模型 |
| Google DeepMind：Gemini、Gemma | 官方組織與模型目錄 [4] | Gemini 服務存取與 Gemma 權重條款要分開看 |

**Meta 的名稱還要對照存取方式。** Muse 是面向使用者的 agent，Muse Code 是終端程式開發 agent。Muse Wonder Full 透過符合條件的 Muse Code 訂閱提供；把 `muse-wonder-1.0` API 的推理強度提高到 `max`，不會選到 Full 版本。Spark Open 與 Glimmer 的下載頁則各自標示實際權重。[20, 21, 22, 33]

要讓比較可以重做，API 提供帶日期的快照時就固定該版本，否則記錄別名、回傳的模型識別碼與日期。下載權重則記錄儲存庫版本識別碼（revision）、量化與執行環境，同時固定提示、工具、token 預算及重試政策。版本連結能辨認成果，不能證明它在你的任務勝出。

本地部署不能只用參數量估算記憶體。權重精度、執行環境額外用量、隨對話增長的注意力快取，以及同時處理的請求數都會影響需求。請用實際硬體測試預定的情境長度與併發量；能載入模型，不代表互動速度足夠。

## 每個評測究竟在問什麼

評測是在特定規則下測量特定任務。先看任務定義，再看分數。

| 評測或比較 | 主要問題 | 結果不能直接證明什麼 |
| --- | --- | --- |
| [SWE-bench 排行榜](https://www.swebench.com/)與 [Verified 資料集](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified) [30] | 系統能否提出通過評測儲存庫測試的修補？[9] | 整體軟體品質、所有回歸問題，或換一套 agent harness 後的表現 |
| [Terminal-Bench 4.0](https://www.tbench.ai/)與[版本化任務目錄](https://hub.harborframework.com/datasets) [34] | Agent 能否完成終端環境中的可執行任務？[10] | 脫離工具、預算與 agent 實作後，模型本身的能力分數 |
| [Arena 一般成對比較](https://arena.ai/faq/) | 抽樣投票者較偏好哪個回答？[11] | 事實正確性或你的工作流程是否完成 |
| [Berkeley Function-Calling Leaderboard V4](https://gorilla.cs.berkeley.edu/leaderboard.html) | 模型能否依測試規則選擇並組成工具呼叫？[12] | 整套正式業務流程能可靠執行 |
| [Artificial Analysis 比較頁](https://artificialanalysis.ai/)與[方法](https://artificialanalysis.ai/methodology/) [35] | 模型在指定品質、效能與價格測量上如何比較？[13] | 跨越不同評測版本仍永久有效的通用指數 |
| [LiveCodeBench 版本與排行榜](https://livecodebench.github.io/leaderboard.html) [31] | 模型能否解出所選時間區間的程式題？ | 儲存庫尺度的 agent 可靠性，或跨出題日期與取樣設定的等價結果 |
| [HELM 評估框架](https://github.com/stanford-crfm/helm) [32] | 模型在所選情境與指標的表現如何？ | 能取代各種部署驗收的單一分數 |

每筆結果都附上確切測試套件／版本、測試切分或日期區間、模型快照、agent／harness commit、工具呼叫模式、推理強度與嘗試預算。BFCL 要分清原生函式呼叫與提示式呼叫；SWE-bench 要用同一資料集及 agent 設定；Artificial Analysis 要保留指數／方法版本與推理強度檢視。這些連結是持續更新的評估入口，不是凍結的名次表。[12, 30, 31, 32, 34, 35]

Terminal-Bench 查核時的網站使用 4.0 版；不同版本的分數不能直接放在一起比較。Arena 的一般成對比較與 Agent Mode 採不同評估設計，也不能把所有結果都稱為同一種評分。[10, 11, 14]

## 真正有助於維運的指標

**任務成功率**是通過預先定義驗收的嘗試比例。看答案前先寫驗收條件，包含保留無關檔案、提供可用引文等限制，而不只是產出看似合理的文字。

**每個驗收成果的成本**是全部試驗支出除以通過驗收的成果數；失敗與重試也要算。人工審查可以另列，或明訂計費方式後納入。若沒有任何成果通過，應直接報告失敗，不能給出誤導性的有限成本。

**延遲**必須先定義起終點。首個 token 的等待時間，描述輸出何時開始；端到端時間，描述可驗收成果何時就緒。請呈現多次試驗的典型與慢尾端表現，不只挑最快的展示。引用 Artificial Analysis 圖表時，要沿用其效能與價格測量定義。[13]

**重複執行的可靠性**與「至少一次成功的機率」不同。能負擔多份獨立草稿的流程，和每次都必須成功的無人值守工作，要求不同。請交代嘗試次數，以及成功如何彙整。

## 排名為什麼可能誤導

公開題目可能與訓練資料相近；評審可能偏好某種回答風格；只改工具描述，也可能在權重不變時改變 agent 行為。增加重試會提高成功機會，也會增加成本。這些現象提醒我們檢查評測程序，而不是放棄評估。

建立一小組有明確檢查方式的私人代表任務，包含一般工作、模糊要求、缺少相依項，以及工具故障。保留起始狀態並檢視失敗紀錄；升級後重跑相同程序。小樣本下兩個候選接近時，請保留不確定性，依操作需求選擇，不急著宣布贏家。

## 新手的選擇路徑

先透過自己能理解的工具使用一個託管模型。寫下成功成果的樣子，保留幾項真實任務作為比較集合。當本地執行、客製化或服務成本帶來具體需求時，再試開放權重模型。選擇能通過驗收的最小系統，工作負載改變時重新評估。

視覺工作可接著讀[影像生成模型選擇](/zh-tw/blog/choosing-image-generation-models/)或[影片生成模型選擇](/zh-tw/blog/choosing-video-generation-models/)。它們的品質條件超出文字模型排名的範圍。
