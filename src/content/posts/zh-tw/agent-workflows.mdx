Agent 工作流程，是從請求走到可用成果的完整路徑。重點不在有幾個 agent 參與，而在系統如何決定要做什麼、在哪裡停下來檢查、遇到每一種失敗如何恢復，以及最後交出什麼。

還不熟悉相關名詞，可以先看 [agent 基礎介紹](/zh-tw/blog/agents-from-prompts-to-systems/)。單一循環的機制（證據關卡、檢查點、重播防護）在 [skills 與 harness](/zh-tw/blog/agent-skills-and-harnesses/) 中說明；這篇則站在更上一層，談整個流程的形狀。各框架的相關說明見[現行選項](#現行選項查核日期-2026-年-11-月-6-日)。

## 重點

- 決定每個決策該放在哪裡：固定的程式碼（可預期的步驟、權限、檢查），還是模型（取決於它觀察到什麼的選擇）。
- 選模式要有理由：串接、路由、平行工作、單一搭配工具的 agent、協調者與工作者，或生成者與評估者。它們是選項，不是成熟度階梯。
- 階段之間設關卡：每個階段產出可檢查的東西，檢查通過後下一階段才開始。
- 為整個任務設定預算（步驟、時間、成本），跨續作累計；沒有新證據卻重複失敗時就停止。
- 依失敗類型恢復；絕不盲目重做一個效果未知的行動。
- 以交接結束：說明產物、實際執行過的檢查，以及尚未完成的部分。

## 決定哪些決策放在哪裡

**固定工作流程**依預先定義的轉換執行，即使其中有步驟呼叫語言模型。**Agent 循環**則讓模型根據觀察選擇下一個行動。許多實用系統會結合兩者：確定性的程式管理存取、順序與檢查，agent 則在某個階段內調查意外的失敗。[1]

| 模式 | 適合什麼情況 | 範例 | 主要失敗風險 |
| --- | --- | --- | --- |
| 串接 | 後一步需要前一步的輸出 | 擷取來源論點、核對，再寫草稿 | 早期錯誤一路傳到後續每一步 |
| 路由 | 不同輸入需要不同程序 | 把文件問題交給文件處理流程 | 分類錯誤而選錯程序 |
| 平行工作 | 子任務獨立，成果能整合 | 檢查互不重疊的參考文獻清單 | 重複工作；輸出彼此不相容 |
| 單一 agent 搭配工具 | 下一步取決於調查結果 | 找出連結檢查失敗的原因 | 反覆嘗試卻沒有新證據 |
| 協調者與工作者 | 要檢查後才知道怎麼拆分 | 分派獨立章節的審閱 | 協調成本與整合缺口 |
| 生成者與評估者 | 有可用的驗收規準 | 起草說明，再逐項核對論點 | 評估者獎勵看似合理的文字，而非正確性 |

通常用三個問題決定模式：

1. **我能預先寫下步驟嗎？** 可以的話，用固定串接或路由，讓模型填內容，而不是控制流程。
2. **子任務彼此獨立嗎？** 只有獨立時平行工作才划算；否則整合成本會吃掉好處。
3. **有獨立的檢查嗎？** 當評估者能測試生成者無法偽造的東西（例如執行測試、比對引用的來源）時，生成者與評估者的循環才有效。兩個有相同盲點的模型，並不構成獨立檢查。[1, 3]

## 沿著整條路徑走，並設置關卡

一般路徑是**請求 → 任務約定 → 計畫 → 工具工作 → 驗證 → 交接**。每個箭頭都是一道**關卡**：目前階段產出可檢查的東西後，下一階段才開始。

| 階段 | 產出什麼 | 通往下一階段的關卡 |
| --- | --- | --- |
| 任務約定 | 目標、輸入、允許的行動、驗收條件 | 成果與允許的行動都沒有歧義 |
| 計畫 | 小步驟與相依關係 | 下一個行動可以執行，且在範圍內 |
| 工具工作 | 修改後的產物與行動結果 | 變更真的存在於環境中，而不只是在對話紀錄裡 |
| 驗證 | 綁定目前產物版本的檢查結果 | 必要檢查通過，或缺口已明確記錄 |
| 交接 | 產物位置、證據、未完成事項 | 其他人或下一次執行不必再問就能接手 |

驗證失敗時，帶著失敗證據回到相關的工作步驟，而不是全部重來。缺少資訊或權限時，保存進度並指出缺什麼。計畫是工作狀態的一部分：觀察改變問題時就更新它，也不要把計畫項目全部勾完，誤當成已達到驗收條件。儲存庫指引與容易理解的專案文件，能在每個階段協助 agent 找到正確的指令與限制。[2]

**人工核准該放在哪裡。** 把核准放在真正的新邊界：發布、寄送、刪除、花費，或在約定範圍之外行動。對每一次讀取都要求核准，只會讓人養成不看就按「同意」的習慣，比完全沒有關卡更糟。任務約定已經授權的工作，應該不被打斷地進行。

**預算。** 為步驟、實際經過時間與花費設定一個跨暫停與續作累計的總預算；每次續作就歸零的單次呼叫上限，什麼都限制不了。再加一條「卡住」規則，例如同一項檢查失敗三次且沒有新資訊就停止，並回報怎樣才能解開。

## 範例：修復一章的閱讀連結

請求：「修正這章失效的閱讀連結，並說明仍無法確認的來源。」

1. **任務約定。** 章節檔案、允許修改的檔案（只有那一個）、預期輸出（可審閱的變更加一份簡短報告），以及連結檢查指令。修改該章已獲授權；發布網站則沒有。
2. **查看起始狀態。** 閱讀儲存庫指引、檢查是否有他人尚未提交的修改，並列出確切失效的連結。*關卡：* 已有一份具體的清單。
3. **取得證據。** 開啟每個候選來源，核對標題、作者與版本，再決定替代連結；只找到相似名稱的網頁還不夠。*關卡：* 每個替代連結都有核對過的來源，或標為未解決。
4. **做集中修改。** 更新連結，以及因新來源而不再正確的句子。*關卡：* 差異只涉及允許的檔案。
5. **驗證。** 執行連結檢查與內容檢查，再查看差異。HTTP 回應成功，不等於連結指向預期的作品。*關卡：* 檢查在這個版本上通過。
6. **交接。** 報告變更的檔案、真正執行過的檢查及其結果，以及未解決的來源。

第二位工作者可以平行核對另一章。兩位工作者在沒有整合步驟時，不應同時重寫同一段落，而審閱者也不會取代連結檢查。

## 依失敗類型恢復

| 觀察到什麼 | 失敗類型 | 下一步 |
| --- | --- | --- |
| 來源暫時無法連線 | 暫時性 | 在預算內以退避方式重試，或記錄為無法取得 |
| 缺少必要檔案或相依項 | 缺少輸入 | 尋找文件記載的輸入，或指出確切缺少的需求 |
| 編輯後測試失敗 | 工作本身有缺陷 | 查看失敗原因並修正相關變更 |
| 寫入逾時 | 結果未知 | 先確認是否已生效再重做；服務提供冪等鍵（idempotency key）時就使用 |
| 下一個行動超出已授權範圍 | 權限 | 準備可審閱的成果，再請求具體的授權 |
| 嘗試沒有產生新證據 | 卡住 | 停止、保存狀態，並說明需要什麼才能繼續 |

「結果未知」那一列是造成實際傷害的來源：付款、訊息或工單被建立兩次。檢查點記錄工作流程走到哪裡，但不能證明遠端行動恰好發生一次。具體機制（穩定的行動身分、收據、重試前先對帳）在[第 2 部分](/zh-tw/blog/agent-skills-and-harnesses/)有可執行的示範。已保存的檢查結果要綁定它所檢查的產物版本，這樣後續編輯就不會沿用舊的「通過」。

## 讓人用得上的交接

不論成功與否，每次執行都以固定格式的交接結束。例如：

```text
Result: chapter links repaired (2 of 3); 1 unresolved.
Artifact: content/chapter-04.md (changed lines 112, 187)
Checks run: link-check -> pass; content-check -> pass (both on the final revision)
Unresolved: [7] publisher page removed; no archived copy with matching title found.
Not done (out of scope): site build and deployment.
Next action: decide whether to cite the preprint instead of the removed page.
```

交接會說明驗證了什麼、怎麼驗證，區分「沒做」與「失敗」，並給出唯一的下一步。它很短，因為細節留在產物與紀錄中，可透過它指出的路徑找到。

## 先評估流程，再改善它

從你的實際工作建立一個小型評估集：一般任務、模糊輸入、來源缺失、工具故障與中斷的執行。評分時看最終的環境（檔案、工單、訂位），而不是對話紀錄；agent 說已修好連結，不等於連結真的修好了。[4] 記錄通過驗收的成果、總成本、耗時、重試與人工修正，並把用來調整的案例和用來評判的案例分開。[模型評測指南](/zh-tw/blog/models-benchmarks-and-people/)說明如何解讀小樣本上的通過率，以及為什麼重複執行的可靠度不同於多次中取最佳的成功率。

接著一次只改一件事：更清楚的輸入、更好的工具、更強的檢查，或更精簡的交接。只有在量測到瓶頸時，才增加工作者或評估者。知道介面或框架必須承擔哪些責任之後，再利用[工具選擇指南](/zh-tw/blog/choosing-agent-tools/)來選擇。
