Agent 工作流程，是從請求走到可用成果的完整路徑。重點不在參與的 agent 有幾個，而在系統如何決定下一步、保留進度、發現失敗，以及判斷何時停止。

還不熟悉相關名詞，可以先看 [agent 基礎介紹](/zh-tw/blog/agents-from-prompts-to-systems/)。這篇把概念接成具體流程。來源查核日期為 **2026 年 11 月 5 日**；以下範例是原創設計練習，不是產品實測比較。

## 決定哪些地方需要判斷

**固定工作流程**依預先定義的轉換執行，即使其中有步驟呼叫語言模型，仍然可以是固定流程。**Agent 循環**則讓模型根據觀察選擇行動。許多實用系統會結合兩者：確定性的程式管理存取與檢查，agent 負責調查意外失敗。Anthropic 的流程分類明確區分這兩種設計。[1]

| 模式 | 適合什麼情況 | 範例 | 主要失敗風險 |
| --- | --- | --- | --- |
| 串接 | 後一步需要前一步的輸出 | 擷取來源論點、核對，再寫草稿 | 早期錯誤一路傳到後續步驟 |
| 路由 | 不同輸入需要不同程序 | 把文件問題交給文件處理流程 | 分類錯誤而選錯程序 |
| 平行工作 | 任務獨立，成果能整合 | 檢查互不重疊的參考文獻清單 | 重複工作或輸出彼此不相容 |
| 單一 agent 搭配工具 | 下一步取決於調查結果 | 找出連結檢查失敗的原因 | 反覆嘗試卻沒有新證據 |
| 協調者與工作者 | 檢查後能拆成不同工作 | 分派獨立章節的審閱 | 協調成本與整合缺口 |
| 生成者與評估者 | 有可用的驗收規準 | 起草說明，再核對論點 | 評估者獎勵看似合理的文字，卻沒確認正確性 |

這些是設計選項，不是成熟度階梯。簡短的固定流程可能就是最佳解法。只有在輸出負責人、格式與整合步驟都清楚時，再增加工作者。[1]

## 看懂整條路徑

一般路徑是**請求 → 任務約定 → 計畫 → 工具工作 → 驗證 → 交接**。驗證失敗時，帶著失敗證據回到相關工作步驟；缺少資訊或權限時，保存進度並指出缺什麼，不必每次從頭開始。

| 階段 | 產出什麼 | 何時前進 |
| --- | --- | --- |
| 任務約定 | 目標、輸入、範圍、驗收條件 | 成果與允許行動已清楚 |
| 計畫 | 小步驟與相依關係 | 下一個行動可以執行 |
| 工具工作 | 修改後的產物與行動結果 | 預定變更真正存在於環境中 |
| 驗證 | 針對目前產物的檢查 | 必要檢查通過，或缺口已明確記錄 |
| 恢復 | 修正後狀態或明確阻礙 | 原因已處理，或後續需要新輸入 |
| 交接 | 產物位置、證據、剩餘工作 | 其他人或下一次執行能理解結果 |

計畫是工作狀態的一部分。觀察改變問題時，就更新計畫；不要把待辦方塊全部勾完，誤當成已通過驗收。儲存庫指引與容易理解的專案文件，能協助 agent 找到正確指令與限制。[2]

## 範例：修復課程的閱讀連結

假設請求是：「修正這章失效的閱讀連結，並說明仍無法確認的來源。」一套容易檢查的流程如下：

1. **定義任務約定。** 確認章節、可修改檔案、預期產物與連結檢查指令。這個任務已授權修改該章；發布網站則是另一個行動，除非先前已有授權。
2. **查看起始狀態。** 閱讀儲存庫指引、檢查本地修改，找出確切失敗連結，並保留無關工作。
3. **取得證據。** 開啟第一手來源，核對標題、作者與版本，再決定替代連結；只找到相似名稱的網頁還不夠。
4. **做集中修改。** 更新目標連結，以及因來源改變而不再正確的說明。仍取不到的證據要明確標示。
5. **驗證產物。** 執行相關連結與內容檢查、查看差異，確認連結確實指向預期作品。HTTP 回應成功，不等於論文身分正確。
6. **交出有用的結果。** 說明變更檔案、真正執行過的檢查與尚未解決的來源，附上產物或審閱位置，而不只是說「完成」。

第二位工作者可以獨立核對另一份參考清單；沒有整合設計時，不應讓兩位工作者同時重寫同一段落。安排審閱者，也不會取代可執行檢查。

## 保存足夠的狀態，才能續作

檢查點記錄執行到哪裡。這個範例可以保存任務約定、起始版本、變更檔案、來源核對結果、失敗檢查與下一步。詳細紀錄透過穩定路徑保留，不必把每次工具回應全部複製到下一個提示裡。

LangGraph 的持久化文件說明檢查點與續作機制，但外部行動如何重試，仍由應用決定。[3] 長時間執行 agent 的工程報告，也透過漸進工作與明確交接，讓下一個工作階段從一致狀態繼續。[4]

檢查點不代表遠端操作已被保證恰好執行一次。寫入成功但回應遺失時，重做可能產生重複結果。服務提供冪等機制時可使用它，否則重試前應查看並核對目標狀態。已保存的檢查結果也要綁定受檢查的產物版本；後續編輯可能使先前的通過結果失效。

## 依失敗原因恢復

| 觀察到什麼 | 下一步 |
| --- | --- |
| 來源暫時無法連線 | 在既定額度內重試，或記錄無法取得的證據 |
| 缺少必要檔案或相依項 | 尋找文件記載的輸入，或指出確切缺少的需求 |
| 編輯後測試失敗 | 查看失敗原因並修正相關變更 |
| 寫入逾時 | 先確認是否已生效，再決定是否重做 |
| 行動超出已授權範圍 | 準備可審閱成果，再請求缺少的授權 |
| 重複嘗試沒有新證據 | 停止循環、保存狀態，說明需要什麼才能繼續 |

這些是應用設計建議。額度應跨續作累計，而不只是每次呼叫都重新歸零的上限。既有授權應持續可用；確認關卡應放在真正的新邊界，例如尚未授權的發布或破壞性操作。

## 先評估流程，再改善它

測試一般任務、模糊輸入、來源缺失、工具故障，以及中斷後續作。同時查看最終環境與對話：agent 說已修好連結，不等於檔案變更真的通過驗證。Agent 評估指引也強調，要區分對話行為與任務結果。[5]

記錄通過驗收的成果、總成本、耗時、重試與人工修正。評估案例應與調整程序時使用的範例分開。[模型與評測指南](/zh-tw/blog/models-benchmarks-and-people/)說明了為什麼模型排名無法單獨替你選出最佳流程。

先從一個有範圍的任務與一位工作者開始，再改善已觀察到的瓶頸：更清楚的輸入、更好的工具、更強的檢查，或更精簡的交接。理解工具需要承擔哪些責任後，再利用[工具選擇指南](/zh-tw/blog/choosing-agent-tools/)決定介面或框架。
