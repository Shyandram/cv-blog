An agent workflow is the path from a request to a result someone can use. The interesting part is not how many agents participate. It is how the system decides what to do, preserves progress, detects failure, and knows when to stop.

Start with [the agent fundamentals](/en/blog/agents-from-prompts-to-systems/) if the terms are new. This article turns those ideas into a concrete workflow. Sources were checked on **5 November 2026**; the example below is an original design exercise, not a measured product comparison.

## Choose where decisions belong

A **fixed workflow** follows predefined transitions, even if some steps call a language model. An **agent loop** lets the model choose actions in response to observations. Many useful applications combine them: deterministic code controls access and checks, while an agent investigates an unexpected failure. Anthropic's workflow taxonomy makes this distinction explicit. [1]

| Pattern | Use it when | Example | Main failure to watch |
| --- | --- | --- | --- |
| Chaining | Later steps need earlier outputs | Extract source claims, check them, then draft | An early error flows into every later step |
| Routing | Inputs require different procedures | Send a documentation issue to a documentation workflow | Wrong classification selects the wrong procedure |
| Parallel work | Tasks are independent and can be integrated | Check separate reference lists | Duplicate effort or incompatible outputs |
| One agent with tools | The next action depends on what it discovers | Investigate why a link check fails | Repeated attempts without useful new evidence |
| Coordinator and workers | A task can be divided after inspection | Assign independent chapter reviews | Coordination costs and integration gaps |
| Generator and evaluator | A useful acceptance rubric exists | Draft an explanation, then check its claims | The evaluator rewards plausible text instead of correctness |

These are design options, not a maturity ladder. A short fixed chain can be the best solution. Add another worker only when its output has a clear owner, format, and integration step. [1]

## Follow the whole path

The normal route is **request → task contract → plan → tool work → verification → handoff**. If verification fails, return to the relevant work step with the failure evidence. If information or authority is missing, preserve progress and identify the missing input. Do not restart everything by default.

| Stage | Produce | Move on when |
| --- | --- | --- |
| Task contract | Goal, inputs, boundaries, acceptance criteria | The result and permitted actions are clear |
| Plan | Small steps and dependencies | The next action is executable |
| Tool work | A changed artifact and action results | The proposed change exists in the environment |
| Verification | Checks against the current artifact | Required checks pass or a gap is explicitly recorded |
| Recovery | A corrected state or a precise blocker | The cause is addressed, or further work needs input |
| Handoff | Artifact location, evidence, remaining work | Another person or run can understand the outcome |

The plan is working state. Revise it when observations change the problem; do not confuse completing plan checkboxes with meeting the acceptance criteria. Repository instructions and readable project documentation help an agent locate the right commands and constraints. [2]

## Example: repair a course's reading links

Suppose the request is: “Fix broken reading links in this chapter and explain any unresolved sources.” A useful workflow is small enough to inspect:

1. **Define the contract.** Identify the chapter, allowed files, expected output, and link-check command. Editing the chapter is authorized by this task; publishing the site is a separate action unless already authorized.
2. **Inspect the starting state.** Read repository instructions, check local changes, and identify the exact failing links. Preserve unrelated work.
3. **Collect evidence.** Open each primary source. Match the title, authors, and version before choosing a replacement. A similarly named page is not sufficient.
4. **Apply a focused change.** Update the intended link and any explanation made inaccurate by the new source. Leave unavailable evidence explicit.
5. **Verify the artifact.** Run the relevant link check and content checks, inspect the diff, and confirm that the link points to the intended work. A successful HTTP response alone does not establish source identity.
6. **Deliver a useful handoff.** Report the changed file, checks actually run, and unresolved sources. Include the artifact or review location rather than only saying “done.”

A second worker could independently verify a different reference list. Two workers should not simultaneously rewrite the same paragraph without an integration design. Assigning a reviewer also does not remove the need for executable checks.

## Save enough state to resume

A checkpoint records where execution has reached. For this example, save the task contract, starting revision, changed files, source matches, failed checks, and next action. Keep detailed logs available through stable paths instead of copying every tool response into the next prompt.

LangGraph's persistence documentation describes checkpoints and resumption. The application still decides how external effects are retried. [3] Long-running agent engineering reports similarly use incremental work and explicit handoffs so a later session can continue from a coherent state. [4]

A checkpoint is not proof that a remote action happened exactly once. If a write succeeds but its response is lost, repeating it may create a duplicate. Use the service's idempotency support when available, or inspect and reconcile the target before retrying. Bind saved check results to the artifact revision they examined: an edit can invalidate an earlier passing result.

## Recover according to the failure

| Observation | Next action |
| --- | --- |
| A source is temporarily unreachable | Retry within the defined budget or record the unavailable evidence |
| A required file or dependency is missing | Locate the documented input or report the precise missing requirement |
| A test fails after an edit | Inspect the failure and repair the relevant change |
| A write timed out | Check whether it took effect before repeating it |
| A requested action exceeds the authorized scope | Prepare the reviewable result and request the missing authorization |
| Repeated attempts produce no new evidence | Stop the loop, preserve state, and explain what would unblock it |

These are application design recommendations. Define a total budget across resumptions, not merely a per-call limit that resets every time. Existing authorization should remain usable; approval gates belong at genuinely new boundaries, such as an otherwise unauthorized publication or destructive operation.

For an executable miniature of replay handling and evidence gating, see [skills and harnesses](/en/blog/agent-skills-and-harnesses/). For sessions and scheduled execution in a concrete application, continue to [OpenClaw operation](/en/blog/openclaw-practical-agent-operations/).

## Evaluate the workflow, then improve it

Use ordinary tasks, ambiguous inputs, missing sources, tool failures, and interrupted runs. Check the final environment as well as the transcript. An agent's statement that it fixed a link is not equivalent to a verified file change. Agent evaluation guidance emphasizes this distinction between conversational behavior and task outcomes. [5]

Record accepted results, total cost, elapsed time, retries, and human corrections. Keep evaluation cases separate from examples used to tune the procedure. The [model and benchmark guide](/en/blog/models-benchmarks-and-people/) explains why model rankings alone cannot select the best workflow.

Start with one bounded task and one worker. Improve the observed bottleneck: clearer input, a better tool, a stronger check, or a smaller handoff. Use [the tool-selection guide](/en/blog/choosing-agent-tools/) to choose the interface or framework after you understand which responsibilities it must support.
