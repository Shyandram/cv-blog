A model is a component of a working system. A leaderboard can help you shortlist candidates, but your tools, instructions, data, and acceptance criteria determine whether a candidate is useful. Read this after [choosing agent tools](/en/blog/choosing-agent-tools/).

Background sources were checked on **5 November 2026**; the version and benchmark links below were refreshed on **6 November 2026**. These are identifiable choices to investigate, not an exhaustive model inventory or a reproduced performance ranking. Product names, licensing, and availability can change independently.

## Hosted models and open weights

Hosted services handle inference operations; you evaluate their interfaces, retention settings, availability, and costs. Downloadable weights let you choose where inference runs, but you also take responsibility for memory, serving, upgrades, and monitoring. Open weights do not automatically mean open training data or an unrestricted license.

**Meta names need an access check.** Muse is the consumer agent; Muse Code is a terminal coding agent. Muse Wonder Full is available through qualifying Muse Code subscriptions, not the `muse-wonder-1.0` API ID with effort raised to `max`. The Spark Open and Glimmer download pages identify the weight artifacts separately. [20, 21, 22, 33]

For a repeatable comparison, pin a dated API snapshot when offered; otherwise log the alias, returned model identifier and date. For weights, record the repository revision, quantization and runtime. Keep the prompt, tools, token budget and retry policy fixed. A release link identifies an artifact; it does not prove that the artifact wins your task.

For local deployment, parameter count alone is not a memory budget. Weight precision, runtime overhead, the attention cache used for the growing conversation, and simultaneous requests all matter. Test the intended context length and concurrency on your actual hardware. A model that loads successfully can still be too slow for interactive work.

## What each benchmark asks

Benchmarks measure particular tasks under particular rules. Begin with the task definition, then read the score.

| Benchmark or comparison | Main question | What the result does not establish |
| --- | --- | --- |
| [SWE-bench leaderboards](https://www.swebench.com/) and [Verified dataset](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified) [30] | Can a system produce patches that pass the benchmark's repository tests? [9] | General software quality, every regression, or performance with a different agent harness |
| [Terminal-Bench 4.0](https://www.tbench.ai/) and [versioned task registry](https://hub.harborframework.com/datasets) [34] | Can an agent complete executable tasks in a terminal environment? [10] | A model-only ability score independent of tools, budgets, and agent implementation |
| [Arena standard pairwise comparisons](https://arena.ai/faq/) | Which response do sampled voters prefer? [11] | Factual correctness or successful completion of your workflow |
| [Berkeley Function-Calling Leaderboard V4](https://gorilla.cs.berkeley.edu/leaderboard.html) | Can a model choose and construct tool calls under the suite's rules? [12] | Reliable execution of an entire production business process |
| [Artificial Analysis comparisons](https://artificialanalysis.ai/) and [methodology](https://artificialanalysis.ai/methodology/) [35] | How do tested models compare on specified quality, performance, and price measurements? [13] | A timeless universal index across changing evaluation versions |
| [LiveCodeBench release and leaderboard](https://livecodebench.github.io/leaderboard.html) [31] | Can a model solve the selected time-window's coding tasks? | Repository-scale agent reliability or equal results across different problem dates and sampling settings |
| [HELM evaluation framework](https://github.com/stanford-crfm/helm) [32] | How does a model behave across the selected scenarios and metrics? | A single score that replaces every deployment-specific test |

Keep the exact suite/release, task split or date window, model snapshot, agent/harness commit, tool-calling mode, reasoning effort and attempt budget beside each result. For BFCL, distinguish native function calling from prompted calls; for SWE-bench, choose the same dataset and agent configuration. For Artificial Analysis, save the index/methodology version and effort view. These links are live evaluation entry points, not a frozen ranking. [12, 30, 31, 32, 34, 35]

Terminal-Bench's current site reports version 4.0; scores from a different version are not automatically comparable. Arena's standard pairwise methodology and its Agent Mode use different evaluation designs; do not label every Arena result the same kind of rating. [10, 11, 14]

## Metrics that help you operate a system

**Task success rate** is the fraction of attempts meeting a predefined acceptance test. Write the test before reading the answers. Include constraints such as preserving unrelated files or returning usable citations, not only producing a plausible-looking response.

**Cost per accepted result** divides all trial spending, including failed attempts and retries, by the number of accepted outputs. Report human review separately or include it with an explicit accounting rule. If no output passes, report that failure instead of presenting a misleading finite cost.

**Latency** needs a boundary. Time to first token describes when output begins; end-to-end time describes when an accepted artifact is ready. Report typical and slow-tail behavior across trials rather than the best demonstration. Artificial Analysis explains its measured performance and pricing boundaries; use those definitions when quoting its charts. [13]

**Reliability across repeated runs** differs from the chance that at least one attempt succeeds. A workflow that can afford multiple independent drafts has different requirements from an unattended job that must work on every run. State how many attempts and how success was aggregated.

## Why rankings can mislead

A public task may resemble training data. A judge may favor response style. A changed tool description can alter agent behavior without changing model weights. More retries can improve success while increasing cost. These are reasons to inspect the protocol, not reasons to discard evaluation.

Build a small private set of representative tasks with known checks. Include ordinary work, an ambiguous request, a missing dependency, and a tool failure. Save the starting state and review unsuccessful attempts. Repeat the same protocol after an upgrade. If two candidates are close on a small sample, report the uncertainty and prefer the operational fit rather than declaring a winner.

## A beginner's selection path

Start with one hosted model through a tool you can understand. Write down what a successful result looks like, and retain a few real tasks as a comparison set. Try an open-weight alternative when local operation, customization, or serving economics gives you a concrete reason. Choose the smallest system that meets your checks, then revisit the decision when the workload changes.

For visual work, continue to [image-generation selection](/en/blog/choosing-image-generation-models/) or [video-generation selection](/en/blog/choosing-video-generation-models/). Their quality criteria extend beyond text-model rankings.
