An assistant can explain how to fix a broken link. An agent can inspect the repository, identify the target, edit the link, run a check, and return a reviewable change. The useful difference is the feedback loop: it can observe what happened and choose what to do next.

This three-part series follows that loop from everyday use to implementation and operation. **Start here if you have used a chatbot but have not built an agent.** Basic familiarity with files and commands is enough; training a language model is not a prerequisite.

## Start with the work you want finished

Consider a weekly literature digest. A useful outcome is a local document with a short description of each selected paper, a primary-source link, and an explicit list of uncertainties. “Research everything about agents” leaves the search space and completion test open. “Prepare this digest from these sources, then stop before sending it” gives the system a task it can finish.

The same principle applies to code. Specify the observable behavior, the allowed files, a validation command, and the artifact you expect. A plan is useful when it reduces uncertainty; a long plan is not itself progress.

Here is an original task template you can adapt:

```text
Goal: prepare a short digest of the three supplied papers.
Inputs: the supplied PDFs and their official publication pages.
Output: a local draft with a claim, evidence, limitation, and source for each.
Allowed actions: read these sources and write inside the draft directory.
Acceptance: every factual claim has a source; unknowns remain explicit.
Stop: after the draft and source checks; do not send or publish it.
If blocked: preserve completed work and name the missing evidence.
```

This is a task contract, not a magic prompt. A real application must enforce filesystem and sending permissions in its tools. Prompt text alone cannot enforce them. You can keep an existing authorization in force while still requiring review for a new action outside that scope.

For a first attempt, choose work that has a small output and an obvious check: a draft, a table extracted from known documents, or a patch to a reproducible bug. Review the artifact and the checks. A confident final message is weak evidence of success.

## The parts of an agent

The **model** proposes actions. **Tools** let it read or change the environment. **Context** supplies the current task and evidence. A **harness** is the surrounding runtime that manages the loop, tool execution, state, limits, and recovery. A **skill** packages reusable task knowledge that the runtime can make available when relevant. These roles can live in one application; they remain useful distinctions when debugging. [4, 5, 9]

Suppose a digest cites the wrong paper. Ask where the error entered. Was the source absent from context? Did search return a similarly named article? Did a tool truncate the relevant passage? Did the final checker verify only that a URL existed? These causes require different fixes. Rewriting the system prompt may leave the actual failure untouched.

## How the field got here

The dates below mark representative publications and engineering reports. They are not claims that each underlying idea was invented in that year. Older planning, software automation, and information retrieval are part of the background.

### 2022–2023: connecting language to actions and feedback

**ReAct** interleaves reasoning and actions so observations can change the next decision. Its question-answering and interactive-task experiments help explain why retrieving information during a task can be more useful than producing an answer from an initial prompt alone. It does not establish that an unconstrained agent will reliably finish arbitrary work. [1]

**Toolformer** studies learning when and how to call APIs through self-supervised training. That is a different layer from an application passing tool definitions to an already trained model. Adding a calculator to your application does not reproduce Toolformer's training procedure. [2]

**Reflexion** carries textual feedback across trials without updating model weights. The practical connection is a failure note such as “the previous candidate passed syntax checks but missed the empty-input case.” It is more actionable than “try harder,” but feedback can itself be mistaken. The paper's evaluated settings do not make self-criticism an independent correctness test. [3]

### 2024: workflows become a design choice

Anthropic's *Building effective agents* distinguishes predefined workflows from systems where the model chooses its next steps. Routing, parallel work, and evaluator loops become patterns to select for a task, rather than features every agent must contain. [4]

A fixed workflow is often enough for “extract these fields, validate the schema, render a report.” A dynamic loop becomes useful when a failed check changes the investigation. Even then, the outer process can remain deterministic: the model proposes a repair, while code controls permissions, test execution, and completion.

### 2025: context, reusable procedures, and longer tasks

As tasks lengthen, the central question becomes what information survives between steps. Context engineering covers selecting evidence, retrieving details when needed, and compressing or externalizing history. Skills package procedures for selective loading. Long-running harness experiments add initialization, incremental work, and handoff artifacts across sessions. [5–7]

These mechanisms address different problems. Retrieval finds evidence. Compaction shortens the current history. Memory carries selected information across tasks. A checkpoint records recoverable execution state. A skill describes how to perform a recurring task. Calling all five “memory” makes diagnosis harder.

### 2026: the environment and the evaluator become first-class components

OpenAI's harness-engineering report emphasizes repository knowledge, readable environments, and machine-checkable constraints. Anthropic's application-development report separates planning, generation, and evaluation; its managed-agent architecture separates session history, harness, and execution environment. These are engineering case studies, not universal benchmark guarantees. [8–10]

The durable lesson is to make work inspectable: the next run should find the objective, current files, remaining failures, and evidence of completed checks. When the model changes, retest the surrounding machinery too. A workaround for an earlier model can become unnecessary overhead. [10]

## Choose the smallest system that fits

| Situation | A useful starting point | The deciding check |
| --- | --- | --- |
| You need an explanation or rewrite of supplied text | A single model call | Does the response meet a rubric? |
| The steps and input format are predictable | A fixed workflow with validation | Do the intermediate schemas and final artifact pass? |
| Failures require investigation and changing tactics | One agent with a bounded tool loop | Can it recover from a representative failure? |
| Independent investigations can be combined | Parallel workers with a clear output contract | Does integration improve the outcome enough to justify cost? |
| Work spans restarts or external events | Persistent sessions and scheduled/event-driven execution | Can it resume without repeating a side effect? |

This table is a design recommendation, not a performance ranking. Parallelism helps when work is independent. Two agents editing the same file can spend their time resolving each other's changes. A separate reviewer can catch omissions, but two models can also share the same mistaken assumption. Use executable or source-based checks wherever available. [4, 9]

## A practical map of current techniques

### Better inputs and more selective context

Start with a concrete output contract and one representative example. Use structured output for fields that downstream code must parse, then validate the values as well as the shape. A valid date-shaped string can still be the wrong date.

For large sources, retrieve the relevant passages and keep stable source locations. Search, open, inspect, and cite; a search-result snippet is a lead rather than the final evidence. Store bulky tool output outside the prompt and return a small summary with a path back to the original. Dynamic tool discovery similarly avoids loading every tool definition in advance. [5, 11]

### Better execution and recovery

Use typed tool arguments, bounded output, timeouts, and clear error categories. Retry a transient read differently from an invalid request. Before retrying a write whose response was lost, inspect the resulting state or use the service's idempotency mechanism. A timeout does not prove that nothing happened.

Keep a checkpoint with the current task, verified progress, remaining work, artifact locations, and replay identities. Checkpoint support makes pause/resume possible, but external side effects still need explicit handling. Persistent workflow systems such as LangGraph expose checkpoints; application developers still decide what can be safely replayed. [12]

### Better evaluation and controlled improvement

Keep a small regression set containing ordinary successes, likely failures, and boundary cases. Score the final environment as well as the conversation. A report agent should produce a usable report; a booking agent should leave the expected reservation state. Record cost, elapsed time, and interventions alongside quality. [13]

Reflection, prompt optimization, and learned skills can propose improvements. **GEPA** uses trajectory feedback to evolve prompts; its reported comparisons are task-specific, not a reason to assume prompt optimization always replaces model training. Separate the cases used to tune a procedure from the cases used to judge it. [14]

### Newer directions worth following

**Recursive Language Models (RLMs)** treat long input as an external environment that can be inspected and decomposed through programmatic and recursive calls. That is different from pasting a longer document into a larger context window. The relevant question for your workload is whether the extra control flow improves complete evidence coverage at an acceptable cost. [15]

Programmatic tool calling moves filtering, loops, and transformations into code, allowing the model to receive the result that matters. This can reduce unnecessary intermediate text, but the execution environment and data access still need controls. A small direct call is simpler when there is nothing useful to aggregate. [11, 16]

Other active practices include browser/computer interaction, event-driven agents, model routing, prompt caching, and automatic procedure revision. Treat each as an answer to an observed bottleneck. For example, use a browser when the required operation is exposed through the interface, and confirm the resulting state after the click. Use a cheaper model only after checking the tasks routed to it. Cache reusable context only where the provider's semantics fit; a cache is not a source of fresh facts.

## Skills, MCP, ACP, and A2A occupy different layers

| Name | Main concern | It does not by itself provide |
| --- | --- | --- |
| Agent Skills | Portable task instructions and supporting files | New credentials or guaranteed execution |
| MCP | Connecting an application to tools and context providers | A task plan or a complete agent runtime |
| ACP, here meaning Agent Client Protocol | Communication between editors/clients and coding agents | A universal policy for all actions |
| A2A | Communication and task collaboration between agent systems | Shared private state or automatic mutual trust |

These descriptions follow their respective primary specifications. They are complementary interfaces, not four competing names for the same product. Compatibility requires checking the supported version and capabilities on both ends. [6, 17–19]

OpenClaw sits at the application/runtime level: it connects user-facing channels, sessions, tools, and workspaces. It is a concrete place to study how those concerns meet. [20] You do not need to adopt every protocol before using one agent successfully.

## Your first useful experiment

Choose a task you already know how to check. Run a simple baseline, then change one part of the system: add a relevant skill, improve a tool's error message, or provide the missing source. Compare the output and the amount of human correction needed. Keep failed examples.

For the digest example, try a paper with an ambiguous title, a missing PDF, and a source that disagrees with an earlier summary. The useful behavior is to resolve the ambiguity or report the gap. Filling every table cell is not a success if the evidence is absent.

You are ready for the next part when you can name the expected artifact, allowed actions, completion check, and stop condition.
