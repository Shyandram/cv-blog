OpenClaw makes the abstract pieces of an agent visible: a message enters through a channel or interface, a gateway routes it to a session, and a runtime combines the model with tools and workspace information. That makes it a useful case study for learning how to operate an agent, not just prompt one. [1]

**Series:** [1 · Evolution and choosing an approach](/en/blog/agents-from-prompts-to-systems/) → [2 · Skills and harnesses](/en/blog/agent-skills-and-harnesses/) → **3 · OpenClaw in practice**.

**Version boundary.** This article checks official source documentation at commit `34bc6434914728a8d13e8e2dcf6dd98bce6d1d88`, accessed 5 November 2026. A repository's development branch can be ahead of the released package. Check your installed version and its help output before using a command below. The commands were verified against documentation; an authenticated OpenClaw deployment was not run for this article. The Python harness in part 2 was executed locally.

## Follow one request through the system

The **Gateway** is the persistent service joining channels, clients, and runtime operations. A **session** identifies the conversation and execution history. A **workspace** holds the files used for the work. **Skills** supply procedures; **tools** provide actions. A paired **node** can expose capabilities on another device. These are separate responsibilities even when they run on one computer. [1, 2]

If a response fails, locate the stage. A channel can be connected while model access is unavailable. A model can answer while a required command is absent from the execution environment. A skill can be installed but ineligible for the selected agent. “The bot is online” does not distinguish those cases.

## Start with one local draft

Use the same literature-digest task as the earlier articles. Begin with one user, one workspace, one model connection, and a small set of sources. Produce a local draft first. Add a messaging channel or recurring schedule after that path works.

The official quickstart covers supported runtimes, installation methods, provider setup, Gateway status, and the Control UI. Its requirements change with releases, so follow that page for installation rather than copying an old runtime version from a blog. [3]

After installing the release you intend to use and completing its onboarding, these documented commands inspect the setup or open its interface:

```bash
openclaw --version
openclaw gateway status
openclaw dashboard
openclaw skills list --eligible
openclaw skills check
openclaw security audit
```

`dashboard` opens the interface; it does not verify a complete task. `skills check` helps find missing prerequisites. `security audit` reports configuration concerns; it is not a proof that every plugin or workflow is safe. These commands do not install third-party skills or schedule work. [2–4]

Give the agent the digest contract from part 1, then inspect the actual output file. Confirm that the source identities match, missing evidence is visible, and nothing was sent. A small successful run gives you a baseline for later changes.

## Add one skill you understand

For an ordinary local workspace, put the `paper-digest/SKILL.md` example from [part 2](/en/blog/agent-skills-and-harnesses/) under that workspace's `skills/` directory. The pinned documentation gives workspace skills precedence over several shared and bundled sources. Check the selected path when names collide. [2]

Use the installed CLI's skill inspection commands to confirm the skill is found and eligible. Ask explicitly for `paper-digest` on the first test. Then try an ordinary conversational request and confirm the procedure is not applied indiscriminately.

Installing a skill does not install every dependency its instructions mention. If execution happens in a sandbox or on a paired node, the needed files, binaries, and credentials must be available there. Host-side availability is not enough. [2, 5]

### Know which kind of update you made

In the pinned source, ordinary file-backed skills, managed library revisions, and Workshop-generated skills have different refresh rules. File-backed skill discovery can refresh after changes; managed selections preserve a chosen revision until explicitly refreshed; the Workshop documentation describes new-session loading for changed learned skills. Check the relevant mechanism instead of assuming every active session instantly sees the newest file. [2, 6]

For a reproducible test, record the skill's source and revision, start a new session when appropriate, and rerun the same acceptance cases. Review the complete bundle, including scripts and referenced files, when a third-party skill changes. The procedure can change even if its short description does not.

## Keep memory useful and correctable

The current memory documentation distinguishes a compact user-profile file, durable facts and decisions, and dated working notes. `USER.md` holds stable preferences; `MEMORY.md` holds curated non-profile information; `memory/YYYY-MM-DD.md` carries daily observations. The exact loading behavior depends on the configured system. [7]

For the digest project, a useful durable note is “prefer primary papers and mark unavailable experiments,” with an observed date. The complete text of every paper belongs in source storage, not in a bootstrap memory file. An unresolved guess should not silently become a permanent fact.

When a preference changes, supersede the earlier one instead of appending a contradictory instruction. Keep evidence and task state distinguishable: “source B was unavailable on Tuesday” does not imply that it is unavailable forever. Memory retrieval can supply stale information just as ordinary search can.

## Schedule the workflow after validating it manually

A recurring digest needs more than a timer. Define the timezone, source scope, artifact destination, duplicate policy, delivery recipient, budget, and behavior when inputs are missing. Choose whether the task should use an existing session or a fresh one based on what context it actually needs.

**A current migration matters here:** the pinned OpenClaw documentation describes heartbeat monitoring as ordinary automation jobs. `openclaw automations` is the main management interface, and `openclaw cron` remains an alias. Older tutorials that configure heartbeat fields may describe an earlier release. Read the migration page for your version before changing an existing installation. [8, 9]

Inspect existing jobs before adding one:

```bash
openclaw automations list --all
```

Use the documented management interface for your installed version to create a draft-only job, inspect its definition, and review its first run. A job that executes successfully but cannot deliver its result has a different failure from a job that never ran. Record both execution and delivery outcomes.

For duplicate control, this series recommends giving each digest a stable period key, such as the intended week and source-set revision. Save the artifact identity and delivery receipt. The scheduler waking twice should not imply two published copies. This is an application design recommendation, not a claim that one configuration flag provides exactly-once delivery.

## Separate access, tools, and execution

Three questions matter: **who can ask**, **which actions can run**, and **where those actions execute**. A paired sender has passed an access check. That does not make every instruction in a webpage they ask the agent to read authoritative. A tool policy restricts actions; a sandbox restricts parts of the execution environment. [4, 5]

The pinned sandbox documentation states that sandboxing is off by default and that enabling it moves tool execution while the Gateway remains on the host. Do not infer sandboxing from the product name or from an agent merely having a workspace. Verify the effective configuration. [5]

OpenClaw's security guidance treats a Gateway as one trust boundary. Multiple agents or sessions do not by themselves create isolation between mutually adversarial users. Separate credentials and execution boundaries when the trust requirements differ. [4]

For the digest task, source retrieval and local drafting are enough. Publishing can be a distinct, authorized operation against an explicit destination. Keep secret values outside skill files and generated reports. When inspecting traces, retain the information needed to diagnose the failure without copying credentials into a shareable artifact.

## Use learned procedures as reviewable changes

The pinned **Skill Workshop** documentation describes capturing reusable procedures, change history, undo, and a proposal mode for reviewing background learning. This is a concrete example of an agent improving its working instructions. It is not evidence that the underlying model weights changed. [6]

A useful candidate lesson is “when a PDF is unavailable, preserve the verified metadata and mark the missing result.” A poor lesson is “always trust this website” inferred from one successful run. Review the scope of the proposed rule, compare it against earlier failures, and keep a rollback path.

Before accepting a learned revision, rerun a relevant request, an irrelevant request, and a case that previously failed. Retain the older version when the new one makes unrelated work worse. A clean diff and a passing regression set are more persuasive than a claim that the agent has become smarter.

## Diagnose from symptoms

| Symptom | Inspect first | What to avoid |
| --- | --- | --- |
| A message never reaches a run | Channel access, pairing, routing, Gateway status | Rewriting the skill before checking delivery |
| A skill is missing | Selected workspace, source precedence, eligibility | Assuming installation means activation |
| A command works on the host but fails in a task | Actual execution host, dependencies, mounted files | Adding broad permissions to fix a missing binary |
| Old instructions keep appearing | Session selection and skill revision/refresh rules | Updating a different copy with the same name |
| The agent forgets a decision | Saved memory, loading limits, source provenance | Repeating the entire transcript in every prompt |
| A scheduled job produces duplicate output | Run history, trigger identity, application receipts | Retrying an uncertain send blindly |

These are troubleshooting hypotheses, not universal error diagnoses. Use the actual logs and effective settings to confirm them. The official quickstart, skills, memory, and automation documents provide the corresponding inspection surfaces. [2, 3, 7, 8]

## Upgrade through a repeatable acceptance run

Record the installed application, model, skill, and plugin versions. Back up state with the documented method before a migration. Read the release and migration notes, update a test instance where practical, then rerun the same small workflow. The update guide distinguishes package/runtime updates from state migrations and recovery procedures. [10]

Check that a task starts, the intended skill is selected, the draft is created, sources remain accessible, memory is scoped correctly, and a paused task can resume. If a workflow sends messages, test its destination and duplicate behavior in an authorized test channel. Keep an older state backup for a documented rollback; replacing a binary alone may not undo a schema migration.

For your first project, stop at a source-grounded local digest. Once you can inspect its result, explain its permissions, reproduce a failure, and recover a run, you have the foundation for a recurring personal assistant or a more complex development workflow.
