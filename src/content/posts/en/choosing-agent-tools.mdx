Start with where the work happens. An agent inside an editor helps with a different interaction pattern from a scheduled assistant or a framework embedded in your own application. Choosing the model is only one part of choosing the tool.

This guide follows the [agent fundamentals series](/en/blog/agents-from-prompts-to-systems/). Product and repository sources were checked on **5 November 2026**. The comparisons describe documented design and deployment choices, not a hands-on speed ranking or a claim that these are the only mainstream products.

## Separate the tool, model, and service

An open-source client can call a closed model. An open-weight model can run through a paid hosted API. A downloadable application can still send prompts to a remote service. Ask three separate questions: can I inspect and modify the tool's code, can I obtain and run the model weights, and who operates the infrastructure receiving my data?

For example, Codex CLI has an Apache-2.0 repository, while the availability and terms of a selected model are separate. OpenHands has a public development platform, with deployment surfaces that must be evaluated individually. Neither fact means every associated service is locally runnable or free. [1, 6]

## Mainstream coding tools

| Tool | Documented surface | Openness to check | A useful first trial |
| --- | --- | --- | --- |
| Codex CLI | Terminal-based coding agent | Apache-2.0 client; model and hosted-service terms are separate [1] | A small repository repair with an executable test |
| Claude Code | Coding workflow across terminal and supported integrations | Proprietary product; public documentation is not a license to its model weights [2] | A multi-file change with repository instructions |
| Cursor | Editor, agent, and cloud-work surfaces | Proprietary application/service; check the selected model and execution location [3] | Edit, inspect a diff, and interactively revise one feature |
| GitHub Copilot | Repository questions, planned changes, and review on GitHub | Hosted product and account-specific access [4] | A bounded issue whose final artifact is a pull request |
| Gemini CLI | Terminal agent | Apache-2.0 client; provider access is separate [5] | A task that reads local files and uses an approved tool |
| OpenHands | Agent development and software-work platform | Public core repository; inspect deployment and any additional terms [6] | A task in an isolated workspace with repeatable setup |
| Aider | Terminal pair programming with local or cloud models | Apache-2.0 tool; chosen model has its own terms [7] | A narrow change where you review each patch |
| OpenCode | Coding-agent interface with provider choices | MIT tool repository; provider/service terms remain separate [8] | Repeat the same task using two supported model setups |
| Cline | SDK, editor extension, and CLI assistant | Inspect its public repository and the release's license [9] | A change where tool actions and approvals are easy to inspect |

The right first trial is your real work on a small scale. Keep the starting revision, task text, test command, and allowed actions the same. Check the patch, unrelated changes, recovery from a failed command, and the amount of supervision required. A polished interface can matter more than a small benchmark gap if it lets you detect errors earlier.

## When you need to build the application

A framework is appropriate when you need to own state transitions, tool APIs, evaluation, or an application-specific interface. It is additional engineering responsibility, not a shortcut around deciding what success means.

| Tool family | What it supplies | What you still design |
| --- | --- | --- |
| LangGraph | Stateful agent/workflow orchestration and persistence [10] | State schema, replay behavior, task-specific checks |
| OpenAI Agents SDK | Agent and tool primitives, handoffs, and tracing [11] | Business logic, credential boundaries, acceptance tests |
| CrewAI | Agent/task orchestration and workflow structures [12] | Useful division of work and integration quality |
| Browser Use | Browser-agent library and a separate hosted offering [13] | Task scope, authentication handling, and post-action checks |
| n8n | Visual workflow automation with AI capabilities [14] | Trigger rules, error paths, data contracts, and delivery |
| OpenClaw | Channels, sessions, workspace tools, and personal-agent operation [15] | The specific procedure, execution policy, and operating routine |

n8n describes itself as **fair-code**; do not silently equate a visible repository or self-hosting option with an unrestricted open-source license. Likewise, a browser library is not a reason to use screen interaction for an operation already available through a reliable API. [13, 14]

## Match the tool to your situation

If you want to improve code while watching the work, start with one editor or terminal agent. If you want to hand off a well-scoped issue, try a repository/cloud workflow and inspect the resulting change. If the goal is a recurring personal task across channels, inspect OpenClaw's operational model. If the agent is part of your product, begin with a small SDK or explicit workflow and add persistence when the task needs it.

A non-programmer should start with an existing application's supported interface and a reversible task. A developer should start with one tool call and a verifiable result before adding a multi-agent structure. A team should include account administration, auditability, and recovery in the trial rather than evaluating only the best demonstration.

These are selection heuristics. An editor, terminal client, and hosted worker can share the same model yet differ in context assembly, permissions, tools, and checks. Their final behavior is the system's behavior.

## Run a small, fair comparison

Use three tasks: an ordinary success case, an ambiguous request that should trigger clarification, and a task with a deliberate tool failure. For coding, add an existing regression test and a case that catches an incomplete fix. Run each candidate more than once when the model is nondeterministic.

Record the exact application and model version, starting files, enabled tools, budget, output, tests, elapsed time, and human corrections. Include subscription or infrastructure costs where they affect your use. Compare **cost per accepted result**, not only tokens per second or the price of one call. See [the benchmark guide](/en/blog/models-benchmarks-and-people/) for the meaning of those metrics.

Do not install every available connector for the trial. Add the ones required for the chosen work, then verify that the agent can discover and use them. A longer tool list can create more selection ambiguity and make failures harder to trace.

## Before you commit to a workflow

Check whether you can export the output and useful task history, reproduce the environment, understand model/provider routing, and continue work when the service is unavailable. For self-hosting, include upgrades, dependencies, GPU capacity if needed, and incident diagnosis in the cost estimate. Local execution gives control; it also gives you operating work.

Choose the candidate that completes your representative tasks with the least unacceptable failure and manageable supervision. Keep the trial cases: they become the regression suite when the next model or product release arrives.

After choosing the tool, design [the agent workflow](/en/blog/agent-workflows/): define the result, assign bounded steps, check evidence, and recover from failures.
