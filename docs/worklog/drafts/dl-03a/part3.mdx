## Modern view

### What the surveys say

**A Comprehensive Review of YOLO Architectures in Computer Vision: From YOLOv1 to YOLOv8 and YOLO-NAS** (Terven, Córdova-Esparza and Romero-González, *Machine Learning and Knowledge Extraction*, 2023) [@terven] walks through 16 versions in order, starting from the metrics and post-processing, then the architecture and training tricks of each. Its discussion organizes the history by four axes: anchors (absent in YOLO v1, added in YOLOv2, removed again from YOLOX on), framework (Darknet, then PyTorch), backbone (Darknet, then cross-stage partial connections, re-parameterization and architecture search), and the constant speed–accuracy trade-off. It expects COCO to be replaced by harder benchmarks and YOLO models to expand into tracking and multimodal tasks.

**YOLO Evolution: A Comprehensive Benchmark and Architectural Review of YOLOv12, YOLO11, and Their Previous Versions** (Jegham, Koh, Abdelatti and Hendawi, arXiv, 2024, revised 2025) [@jegham] is an experimental comparison rather than a history: it evaluates versions from YOLOv3 to YOLOv12 on datasets chosen for varying object sizes, aspect ratios and small single-class objects, and reports precision, recall, mAP, processing time, GFLOPs and model size. Its takeaway is that no version wins everywhere: in its experiments YOLO11 gave the best overall balance, YOLOv10 was fast but weaker on overlapping objects, and YOLOv12's added complexity did not pay off. Treat these as one group's results on its datasets, not general rankings.

**Ultralytics YOLO Evolution: An Overview of YOLO27, YOLO26, YOLO11, YOLOv8, and YOLOv5** (Sapkota and Karkee, arXiv, 2025, revised 2026) [@sapkota] reviews only the Ultralytics releases, covering architecture, benchmarking, deployment (export and quantization) and applications, and lists open challenges: dense scenes, combining CNNs with transformers, open-vocabulary perception, domain generalization and hardware-aware optimization. It is a third-party review, not an Ultralytics publication.

**Object Detection with Transformers: A Review** (Shehzadi et al., *Sensors*, 2025) [@shehzadi] covers the DETR side: improvements to DETR grouped by backbone, query design and attention mechanism, which is the context for the real-time DETRs.

### The state of the art, 2023–2026

- **NMS-free is becoming the default.** [YOLOv10](#yolov10-nms-free-training-with-dual-assignments) [@yolov10] introduced it to YOLOs in 2024; [YOLO26](#yolo26-a-dfl-free-end-to-end-yolo) [@yolo26] ships it as the default deployment path; every real-time DETR is NMS-free by construction. The announced YOLO27 describes query-based decoding without NMS for its larger models [@yolo27].
- **Attention is affordable.** [YOLOv12](#yolov12-an-attention-centric-yolo) [@yolov12] and [YOLOv13](#yolov13-hypergraph-correlation) [@yolov13] put attention-like modules inside YOLOs, where YOLOv4 could only afford a cheap spatial gate; [RT-DETR](#rt-detr-a-real-time-detr) [@rtdetr] restricts attention to the coarsest level.
- **Pretrained vision transformers as backbones.** [RF-DETR](#rf-detr-architecture-search-on-a-dinov2-backbone) [@rfdetr] and [DEIMv2](#deimv2-dinov3-features-for-real-time-detrs) [@deimv2] start from self-supervised backbones (DINOv2 [@dinov2], DINOv3 [@dinov3]), which mainly helps transfer to new datasets.
- **Training efficiency.** [DEIM](#deim-dense-one-to-one-matching) [@deim] and YOLO26 (with a new optimizer and a progressive loss) target shorter training rather than only higher AP, a direct descendant of YOLOv4's single-GPU goal.

### Open problems

1. **Fair speed comparison.** There is no shared, maintained end-to-end benchmark across devices; most tables still mix conditions, and [RF-DETR](#rf-detr-architecture-search-on-a-dinov2-backbone) shows that even GPU power throttling changes reported latencies.
2. **Small and crowded objects** remain the main accuracy gap at real-time input sizes; YOLO26's small-object assignment and DEIMv2's unchanged small-object AP both illustrate it.
3. **Quantization-friendly heads.** Score and box outputs lose accuracy at INT8, and attention layers complicate low-precision deployment.
4. **Peer review and reproducibility.** YOLOv4 itself and several widely deployed successors have no peer-reviewed paper, released code can differ from the paper, and version numbers are claimed freely; claims need independent checks.
5. **Beyond closed sets.** Bringing open-vocabulary detection to the same latency as closed-set YOLOs without losing accuracy.

## Key takeaways

- "Real-time" is a latency budget for the whole pipeline at batch size 1 on a stated device; a speed number without hardware, precision, input size and timed stages is not comparable. YOLOv4's tables fix the GPU family and batch size but not the precision or the NMS timing.
- A one-stage detector is a backbone, a neck and a dense head. YOLOv4 is CSPDarknet53 (split–process–merge stages), SPP (stride-1 max pooling at 5, 9 and 13), a PANet neck merged by concatenation, and the anchor-based YOLOv3 head at strides 8, 16 and 32.
- The bag of freebies changes only training (Mosaic, self-adversarial training, DropBlock, label smoothing, CmBN, CIoU, several anchors per object, the grid-sensitivity fix, cosine annealing, genetic search); the bag of specials adds a small inference cost (Mish, SPP, SAM, PAN, DIoU-NMS).
- The ablations single out Mosaic, IoU-type losses, genetic search, SPP, PAN and point-wise SAM; several freebies hurt in isolation, and some listed components were never tested on the detector.
- The best ImageNet classifier is not automatically the best detector backbone; operation counts do not predict GPU speed.
- What later detectors changed maps onto YOLOv4's components: anchor-free decoupled heads, prediction-aware and then one-to-one assignment (removing NMS), re-parameterized blocks, auxiliary supervision, affordable attention and new box representations.
- Real-time DETRs reach the same speed from the other direction, keeping one-to-one matching and redesigning the encoder, the box representation and the backbone.

### Ultralytics releases without a paper

This note collects the facts about the YOLO versions that Ultralytics released as software, which the chapter does not introduce as papers because there is no paper to introduce.

- **YOLOv5** [@yolov5] was released in June 2020 as a PyTorch code base, a few weeks after YOLOv4, with several model sizes. Its documentation states that Ultralytics has not published a formal research paper for it "due to the rapidly evolving nature of the models". The original YOLOv5 is anchor-based, like YOLOv4; the RT-DETR paper uses it as one of its anchor-based examples [@rtdetr].
- **YOLOv8** [@yolov8] was released on 10 January 2023 in the `ultralytics` Python package. The documentation describes an anchor-free split head and improved backbone and neck, and again states that no paper was published. The YOLO26 paper describes the distribution focal loss as part of the Ultralytics head since YOLOv8 [@yolo26].
- **YOLO11** [@yolo11] was released on 27 September 2024, with improved backbone and neck design and refined training, across detection, segmentation, classification, pose and oriented boxes; no paper. YOLO26 is built on it [@yolo26].
- **YOLO26** was first released as software in January 2026; its paper followed in June 2026, so it has its own introduction in the [Paper guides](#yolo26-a-dfl-free-end-to-end-yolo).
- **YOLO27** is announced on the Ultralytics documentation, which states that the models are undergoing final development and are not yet available [@yolo27]. Treat it as an announcement until weights and a paper exist.
- **Licensing.** The citation entries in the documentation list the AGPL-3.0 license for these releases [@yolov8], [@yolo11], which matters for commercial products.
- **A cautionary case.** A preprint titled "YOLOv14" appeared on arXiv in August 2026 and was withdrawn by its authors about two weeks later, with the comment that the paper needed to be evaluated and revised [@yolov14]. A version number is not a credential.

These releases matter in practice (they are widely deployed and appear in nearly every comparison table of the later papers), but their design decisions are documented only in code and documentation pages, which change over time. When a paper compares against "YOLOv8", check which release and which weights it used.

### Folding a re-parameterized block into one convolution

**Plain version.** A block with three parallel branches (a $3 \times 3$ convolution, a $1 \times 1$ convolution and a shortcut) trains well but runs slowly. Because every branch is linear until the activation, the three can be added into a single $3 \times 3$ convolution after training, and the network computes exactly the same function, faster.

At inference, batch normalization [@bn] is an affine map per channel. For a bias-free convolution with kernel $W$ followed by batch normalization with learned scale $\gamma$, shift $\beta$, and running mean $\mu$ and variance $\sigma^2$,

$$
\text{BN}(W * x) = \gamma\,\frac{W * x - \mu}{\sqrt{\sigma^2 + \epsilon}} + \beta = W' * x + b', \qquad W' = \frac{\gamma}{\sqrt{\sigma^2 + \epsilon}}\,W, \quad b' = \beta - \frac{\gamma\,\mu}{\sqrt{\sigma^2 + \epsilon}},
$$

where $*$ is convolution, $\epsilon$ a small constant, and all operations are per output channel. A $1 \times 1$ kernel is a $3 \times 3$ kernel that is zero except at its centre, and the identity is a $1 \times 1$ kernel equal to the identity matrix across channels. Once each branch is written as a $3 \times 3$ kernel with a bias, the sum of branches is one convolution with the summed kernel and summed bias. This is the structural re-parameterization of RepVGG [@repvgg].

```python
import numpy as np

def conv(x, w, b):
    """'Same' convolution (cross-correlation). x: (C, H, W), w: (O, C, k, k), b: (O,)."""
    k = w.shape[-1]; p = k // 2
    xp = np.pad(x, ((0, 0), (p, p), (p, p)))
    H, W = x.shape[1:]
    out = sum(np.einsum("oc,chw->ohw", w[:, :, i, j], xp[:, i:i + H, j:j + W])
              for i in range(k) for j in range(k))
    return out + b[:, None, None]

def fold_bn(w, gamma, beta, mu, var, eps=1e-5):
    """A bias-free conv followed by inference-mode batch norm -> one conv with a bias."""
    scale = gamma / np.sqrt(var + eps)
    return w * scale[:, None, None, None], beta - mu * scale

rng = np.random.default_rng(0)
C = 4                                                   # channels in = channels out
x = rng.normal(size=(C, 10, 10))
bn = lambda: (rng.uniform(0.5, 1.5, C), rng.normal(size=C), rng.normal(size=C), rng.uniform(0.5, 2, C))
w3, w1 = rng.normal(size=(C, C, 3, 3)), rng.normal(size=(C, C, 1, 1))
bn3, bn1, bn_id = bn(), bn(), bn()

def bn_apply(z, g, b, mu, var, eps=1e-5):
    return g[:, None, None] * (z - mu[:, None, None]) / np.sqrt(var[:, None, None] + eps) + b[:, None, None]

# training-time block: 3x3 branch + 1x1 branch + identity branch, each with its own batch norm
y_train = (bn_apply(conv(x, w3, np.zeros(C)), *bn3) + bn_apply(conv(x, w1, np.zeros(C)), *bn1)
           + bn_apply(x, *bn_id))

# deployment: express every branch as a 3x3 kernel, fold its batch norm, then add the kernels
w1_as3 = np.pad(w1, ((0, 0), (0, 0), (1, 1), (1, 1)))  # 1x1 kernel in the centre of a 3x3 one
w_id = np.zeros((C, C, 3, 3)); w_id[np.arange(C), np.arange(C), 1, 1] = 1.0
folded = [fold_bn(w, *p) for w, p in [(w3, bn3), (w1_as3, bn1), (w_id, bn_id)]]
w_dep, b_dep = sum(f[0] for f in folded), sum(f[1] for f in folded)
y_dep = conv(x, w_dep, b_dep)
print("same output:", np.allclose(y_train, y_dep))
print("branches at training: 3 | convolutions at inference: 1")
```

```text
same output: True
branches at training: 3 | convolutions at inference: 1
```

The folding is exact only for inference-mode batch normalization (fixed running statistics) and only before the nonlinearity. The YOLOv7 paper's "planned" re-parameterization exists because some combinations, such as an identity branch inside a block that already has a residual connection, hurt accuracy [@yolov7], and YOLOv6 reports that folded models can be harder to quantize [@yolov6].
